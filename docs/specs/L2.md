# L2 - Detailed Requirements

Each L2 traces to one L1 in `L1.md`. Every acceptance test names the L2s it covers in a header
comment:

```typescript
// Acceptance Test
// Traces to: L2-011, L2-013
// Description: Pair an Echelon EX-5s from Connect Bike and land on Home
```

The mocks (`docs/mocks/`) are the source of truth for layout and copy; quoted strings are
verbatim from them. The criteria reuse the mocks' cast:

- **The rider:** Sam, on their own Echelon EX-5s at home, on Friday 2026-11-20 at about
  7:30 PM. Sam is at one of three stages:
  - **new rider:** level 1, 0 / 400 XP, no streak, no rides.
  - **mid rider** (the default): level 7, 1,840 / 2,600 XP, 4-day streak, 23 rides, 412 km.
  - **veteran:** level 18, 9,120 / 10,400 XP, 21-day streak, 146 rides, 3,870 km.
- **Riders online:** lena.k, MarcoVelo, priya_spins, jwatts, Ollie R., kenji.cyc and ana_rides.
- **Bots:** Pacer Nova, Rook, Juno, Atlas, Kite, Vale, Moss, Flint and Echo.

Terms are used in one sense only:

- **Resistance:** the level the bike reports.
- **Target resistance:** the level the app asks for.
- **Plan:** the timed segments a ride follows. A **segment** has a kind (warm-up, work, recover,
  steady, cool-down), a duration, a level and a cadence aim.
- **Race:** a ride on a map, against the rider's **ghost** (solo), **bots**, or **riders
  online**.
- **Class:** a catalogue entry, a bike plan that follows a video.
- **World class:** a class that names a 3D world to ride in (L2-080 AC5). **World loading** is
  the screen that gets that world ready before the class starts.
- **Quality level:** how the 3D world is drawn: Ultra, High, Medium or Low (the drawn look).
  **Auto** picks the level and steps it down when frames drop.
- **Session:** one live race or one group class run by the multiplayer service.
- **Ride:** any finished race, class or custom workout, kept in the rider's history.

Breakpoints are named as in the design system: **phone** < 640 px, **sm** ≥ 640 px,
**md** ≥ 768 px, **lg** ≥ 1024 px, **xl** ≥ 1280 px.

## L2-001: Sign in with an email
**Traces to:** L1-001

A rider signs up or signs in with an email address alone. The same screen does both, so nobody
learns whether an address has an account. Mocks: `docs/mocks/pages/sign-in/`, `docs/mocks/pages/sign-in-code/`.

**Acceptance Criteria:**
1. Given a visitor with no session, when they open any screen other than sign-in, the code screen or not-found, then the sign-in screen opens. After signing in, the screen they asked for opens.
2. Given the sign-in screen, when the visitor enters a valid email and chooses "Send my code", then the button reads "Sending your code…" and is disabled until the request ends, and the code screen opens when it succeeds.
3. Given an email that is not a valid address, when the visitor chooses "Send my code", then no code is sent, the field is marked invalid (`aria-invalid="true"`) and the error under it, "Enter an email address like name@example.com.", is announced.
4. Given an email with no account, when the visitor asks for a code, then the API response, its timing class and the screen are the same as for an account. After the code is confirmed, the account is created and the rider is asked for a display name (L2-005).
5. Given the request to send a code fails, when the failure returns, then the email typed is kept, "We couldn't send your code. Check your connection and try again." is announced, and "Send my code" is enabled again.
6. Given the backend, when it stores an email, then it stores it normalised (trimmed, lower-cased domain) and never stores or asks for a password.

## L2-002: Confirm the six-digit code
**Traces to:** L1-001

A six-digit code sent to the email proves the rider owns it.

**Acceptance Criteria:**
1. Given a code has been sent, when the code screen opens, then it names the email the code went to.
2. Given the code screen, when the rider enters the six correct digits, then they are signed in without a further tap. A rider with no paired bike in this browser goes to Connect Bike (L2-011); otherwise Home opens.
3. Given six digits that do not match, when they are entered, then the field is cleared and marked invalid, and "That code doesn't match. Try again." is announced.
4. Given a code sent more than 10 minutes ago, when it is entered, then it is refused with "That code has expired." and a "Send a new code" action.
5. Given the rider pastes a six-digit code or the device offers it, when it is filled in, then it is submitted as if typed. Any character other than a digit is ignored.
6. Given a code, when it has been used once, then it cannot be used again: it is refused as "That code has expired." with "Send a new code".

## L2-003: Resend and limit codes
**Traces to:** L1-001

Codes are short-lived and cannot be guessed or requested without limit.

**Acceptance Criteria:**
1. Given a code was sent less than 30 seconds ago, when the rider looks at "Send a new code", then it is disabled and shows the seconds left.
2. Given 30 seconds have passed, when the rider chooses "Send a new code", then a new code is sent, the earlier code stops working, and a message confirms it was sent.
3. Given five wrong codes for one email, when a sixth is entered, then it is refused even if it is correct with "Too many wrong codes. Send a new code to try again.", and the rider must request a new code.
4. Given five codes requested for one email within an hour, when a sixth is requested, then it is refused with 429 and `Retry-After`, and the screen reads "Too many codes asked for. Try again in 42 minutes.", the minutes rounded up.
5. Given more than 20 code requests from one IP address within an hour, when another arrives, then it is refused the same way.

## L2-004: Sessions
**Traces to:** L1-001

A signed-in rider stays signed in on a device they keep using.

**Acceptance Criteria:**
1. Given a rider signs in, when the session starts, then it lasts 365 days from the rider's last use of Telo Ride on that device, and each use moves the expiry forward.
2. Given a session, when it is stored in the browser, then it is in a cookie that scripts cannot read (`HttpOnly`), is sent only over HTTPS (`Secure`) and is not sent with requests from other sites (`SameSite=Lax` or stricter).
3. Given a session that has ended, when the rider opens a screen that needs one, then L2-001 AC1 applies.
4. Given a session ends during a ride, when the ride finishes, then the ride is kept on the device (L2-135) and sent after the rider signs in again.
5. Given the backend cannot be reached when the app opens, when the rider opens a screen, then it opens as for a signed-in rider: a ride never waits for the network (L2-135). Only an answer that the session has ended (401) opens sign-in.

## L2-005: Display name
**Traces to:** L1-001

The display name is what other riders see on start grids and boards.

**Acceptance Criteria:**
1. Given a new account, when its code is confirmed, then the rider is asked "What should other riders call you?" before going on, and Continue stays disabled until a name is entered.
2. Given a display name, when it is saved, then it is 2 to 24 characters after trimming, made of letters, digits, spaces, `.`, `_` and `-`. Anything else is refused with 400 (`display_name_invalid`) and the field says "Use 2 to 24 characters: letters, digits, spaces, . _ and -."
3. Given a saved display name, when the rider opens Profile, then the headline uses it ("Sam · Level 7") and the rider can change it there.
4. Given a display name, when it appears on any screen, then it is rendered as text, never as HTML.
5. Given a display name, when another rider sees it, then they see only the name, country code and level, never the email.

## L2-006: Sign out and delete an account
**Traces to:** L1-001

**Acceptance Criteria:**
1. Given a signed-in rider, when they choose "Sign out" on Profile, then the session ends on the backend at once, its cookie is cleared, and the sign-in screen opens. If the backend cannot be reached, the rider stays signed in and Settings says "We couldn't sign you out. Check your connection and try again."
2. Given a signed-in rider, when they choose "Delete my account", then a dialog says what is removed (email, display name, progress and ride history) and asks them to type "delete". "Delete my account" stays disabled until they do; case and surrounding spaces do not matter.
3. Given the rider confirms, when deletion succeeds, then every session ends, the sign-in screen opens with "Your account was deleted. Its personal data is erased within 30 days.", and their personal data is erased within 30 days. When it fails, the dialog stays open with the typed word and says "We couldn't delete your account. Check your connection and try again."
4. Given a deleted account, when its email signs in again, then a new, empty account is created.

## L2-007: Supported bikes list
**Traces to:** L1-002

**Acceptance Criteria:**
1. Given Connect Bike, when it opens, then a "Works with" section lists, in order: "Echelon EX-5s", "Echelon EX-3", "Echelon EX-8s" and "Echelon Connect Sport", each "Full control", and "Other FTMS smart bikes", "Beta".

3. Given a bike that advertises FTMS (service `0x1826`) and is not an Echelon, when it is connected, then the app reads Indoor Bike Data and, if the bike grants control, sets its resistance (L2-014).
4. Given a viewport at sm or wider, when the list shows, then it is two columns; on a phone it is one.

## L2-008: Browser support
**Traces to:** L1-002

Web Bluetooth exists only in Chromium browsers (Chrome and Edge on Windows, macOS, Linux,
ChromeOS and Android).

**Acceptance Criteria:**
1. Given a browser without `navigator.bluetooth`, when Connect Bike opens, then the device card is replaced by an alert (`role="alert"`). It reads "This browser can't reach the bike" and "Open Telo Ride in Chrome or Edge on a laptop or Android tablet. Safari and Firefox don't support Web Bluetooth yet.", with "Try again".
2. Given such a browser, when Class Start or Custom workout opens, then a notice under the header reads "Open Telo Ride in Chrome or Edge." with "Bluetooth to the bike only works there — you can look around, but not ride." and **Copy link**. The page stays readable.
3. Given such a browser, when the rider presses **Copy link**, then the page address is copied to the clipboard and the button shows its copied state.
4. Given a supported browser, when any screen opens, then no unsupported-browser message is shown.

## L2-009: Secure context
**Traces to:** L1-002

Browsers allow Web Bluetooth only on HTTPS pages (and `localhost`). On a plain `http` page a Chromium
browser has no `navigator.bluetooth` either, so an insecure page is told to go secure, never to change
browser.

**Acceptance Criteria:**
1. Given a page served over plain `http` other than `localhost`, when Class Start or Custom workout opens, then a notice reads "Open the secure version of this page." with "Bluetooth is blocked on plain http, so the bike can’t connect." and **Open over HTTPS**. The button goes to the same path on `https://`.
2. Given a production deployment, when a request arrives over `http`, then it is redirected to `https` and responses carry `Strict-Transport-Security`.
3. Given a secure context, when any screen opens, then no HTTPS notice is shown.
4. Given a page served over plain `http` other than `localhost`, when Connect Bike opens, then the device card is replaced by an alert (`role="alert"`). It reads "Open the secure version of this page" and "Bluetooth is blocked on plain http, so the bike can’t connect.", with **Open over HTTPS**, which goes to the same path on `https://`.

## L2-010: Blocked rides
**Traces to:** L1-002

When the bike cannot be reached, the screens that start a ride say why and do not start one.

**Acceptance Criteria:**
1. Given an unsupported browser or an insecure page, when Class Start opens, then its Join or Start button is disabled.
2. Given an unsupported browser, when Custom workout opens, then **Start ride** is disabled and described by "Needs Chrome or Edge to reach the bike.". On an insecure page it reads "Needs the HTTPS page to reach the bike.".
3. Given an unsupported browser, when Custom ride opens, then a full panel (`role="alert"`) reads "Open Telo Ride in Chrome or Edge" with an explanation and **Copy link**, and the bike status reads "Bluetooth unavailable in this browser".
4. Given an insecure page, when Custom ride opens, then a panel reads "Open the secure version of this page" with "Browsers only allow Bluetooth on pages served over HTTPS. You’re on {address}." and **Open over HTTPS**.
5. Given any blocked state, when the rider uses Home, Map Select, the Class Library, Profile or Results, then those screens work normally.

## L2-011: Connect Bike
**Traces to:** L1-003

Connect Bike (`/connect`) is the first-run pairing screen. It is also shown when the remembered
bike cannot be found.

**Acceptance Criteria:**
1. Given Connect Bike, when it opens, then it shows the bike photo, "Connect your bike" and "Pedal once to wake it up. Telo Ride reads your power and sets resistance for every hill and interval.", with no app navigation.
2. Given the rider starts a search, when no bike has answered yet, then the card shows a spinner with "Looking for bikes nearby…" (`role="status"`) and a disabled "Searching…" button.
3. Given the rider picked a bike in the browser's list, when the card shows it, then it gives its name (e.g. "Echelon EX-5s") and identifier ("EX5S-141844"). Where the browser can watch advertisements, the signal strength leads the identifier ("Strong signal · EX5S-141844"). Before the rider picks, the card offers "Echelon EX-5s" with "Pair Echelon EX-5s".
4. Given the rider presses Pair, when pairing runs, then the button is disabled with `aria-busy="true"`, a spinner and "Pairing…".
5. Given pairing succeeds, when the bike is connected, then the card shows a check (`aria-label="Paired"`) and a disabled "Paired" button. About half a second later, Home opens; a rider with no rides lands on the new-rider Home.
6. Given a viewport at lg or wider, when Connect Bike shows, then it is two columns with the photo on the left. Below lg, the photo follows the content at up to 28 rem, square.

## L2-012: Choosing the bike
**Traces to:** L1-003

A web page cannot scan in the background. The rider picks the bike once in the browser's own
chooser, which needs a tap or click.

**Acceptance Criteria:**
1. Given Connect Bike, when the rider presses the search or pair action, then `navigator.bluetooth.requestDevice` is called with filters for a name that starts with `ECH` (spelled `ECH`, `Ech` and `ech`, as the chooser's name filter is case-sensitive), for the Echelon service (`0bf669f1-45f2-11e7-9598-0800200c9a66`) and for FTMS (`0x1826`). Heart Rate (`0x180D`) is listed as an optional service. An Echelon bike that advertises its name without the Echelon service is therefore in the list.
2. Given no user gesture, when the app would open the chooser, then it does not; nothing is requested from Bluetooth until the rider acts.
3. Given the rider cancels the chooser, when it closes, then Connect Bike returns to its default state with no error.
4. Given the chooser cannot open (a policy blocks it), when the request fails, then an alert (`role="alert"`) replaces the device card. It reads "Bluetooth is blocked for this page" and "Allow Bluetooth for this site in your browser’s settings, then try again." (any other failure reads "The bike list didn’t open" and "Something went wrong opening your browser’s list of bikes. Try again."), with "Try again".
5. Given the bike list, when the rider does not see their bike, then the hint "Not in the list? Close the Echelon app on your phone — the bike talks to one device at a time." is shown.

## L2-013: Echelon connection and initialisation
**Traces to:** L1-003

Bytes and UUIDs are in `docs/protocol/echelon-ble-frames.md`.

**Acceptance Criteria:**
1. Given an Echelon bike is chosen, when the app connects, then it opens GATT, gets service `0bf669f1-…`, and subscribes to the notify characteristic `0bf669f4-…` before writing anything.
2. Given the subscription is in place, when initialisation runs, then it writes `F0 A1 00 91`, `F0 A3 00 93` and `F0 B0 01 01 A2`, in that order. Each goes to `0bf669f2-…` with response, at least 300 ms after the previous one.
3. Given any write to the bike, when another is pending, then the new one waits. Writes go one at a time in the order requested.
4. Given initialisation completes, when the first notification arrives, then the bike state is `connected`. Its name is the model's name when the device name is an Echelon's (`ECH-EX5S-141844` is "Echelon EX-5s", identified as `EX5S-141844`), otherwise the device name, or the device's identifier if it has none.

## L2-014: FTMS connection and control
**Traces to:** L1-003

Other smart bikes are supported in beta through the Bluetooth SIG Fitness Machine Service.

**Acceptance Criteria:**
1. Given an FTMS bike is chosen, when the app connects, then it subscribes to Indoor Bike Data (`0x2AD2`) and to Fitness Machine Control Point (`0x2AD9`) indications, and reads Supported Resistance Level Range (`0x2AD6`).
2. Given the control point is subscribed, when the app needs to set resistance, then it first writes Request Control (op code `0x00`). Only on a Success response (`0x80 0x00 0x01`) does it send Set Target Resistance Level (op code `0x04`).
3. Given the bike refuses control or has no control point, when a ride runs, then telemetry still works, the resistance controls are disabled, and the bike status says "Read only" with an explanation in Diagnostics.
4. Given the bike's supported range, when the app maps levels 1 to 32 onto it, then level 1 is the minimum, level 32 the maximum, and levels in between are spaced linearly and rounded to the bike's increment.

## L2-015: The remembered bike
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a bike was paired in this browser, when Telo Ride opens, then it goes to Home without Connect Bike. Where `navigator.bluetooth.getDevices()` exists, it reconnects to that bike without the chooser as soon as the bike advertises.
2. Given the remembered bike does not advertise, when a ride is started, then the ride screen shows "Connect your bike" with "Wake the Echelon EX-5s with a few pedal strokes, then pick it from the list your browser shows. We’ll remember it next time." and **Connect bike** (L2-106).
3. Given `getDevices()` is not available, when Telo Ride opens, then the bike is shown as not connected and **Connect bike** is offered where a ride starts.

## L2-016: Keepalive
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given an Echelon bike is connected and initialised, when 5 seconds pass, then between 4 and 6 keepalive frames `F0 A0 01 01 92` have been written, each with response.
2. Given the tab is hidden, when 60 seconds pass, then keepalives keep going at about one a second, timed from the clock rather than counted ticks (L2-133).
3. Given the bike disconnects, when it is gone, then keepalives stop until it reconnects.

## L2-017: Disconnect and recovery
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given the bike is connected, when it disconnects (`gattserverdisconnected`) or any Web Bluetooth call fails, then the bike state becomes `disconnected`. The app retries the same bike every 3 seconds without the chooser until it connects or the rider ends the ride.
2. Given the bike is switched off for an hour, when it is switched on and pedalled, then the app reconnects within one retry without a reload.
3. Given the rider presses **Reconnect**, when the bike is not connected, then the pending retry is cancelled and an attempt starts at once.
4. Given a reconnect succeeds during a ride, when the bike is back, then the current target resistance is sent again before anything else.
5. Given a Web Bluetooth error, when it is shown, then its name and message are rendered as text and go to the console (L2-115).

Switch it on in your computer’s settings — or, if this machine has none, plug in a USB Bluetooth adapter." and **Check again**.

## L2-019: Bike status
**Traces to:** L1-003

**Acceptance Criteria:**
1. Given a connected bike, when the app header shows at lg or wider, then it shows the bike name with the hidden text " connected".
2. Given no connected bike, when the header shows at lg or wider, then the status is red with the title "Bike not connected" and the hidden text " not connected".

## L2-020: Echelon telemetry decoding
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a notification `F0 D2 01 0C CF`, when it is decoded, then resistance is 12.
2. Given a notification `F0 D1 09 00 05 00 00 00 00 00 50 00 1F`, when it is decoded, then cadence is 80 rpm.
3. Given a frame shorter than 4 bytes, with byte 0 other than `F0`, of an unknown type, or a `D1` shorter than 13 bytes, when it arrives, then it is ignored without an error.
4. Given a `D0` frame, when it arrives, then it is ignored without an error.
5. Given no `D1` frame for 5 seconds while connected, when the readouts show, then cadence and power show "—" rather than their last values.

---

## L2-021: FTMS telemetry decoding
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given an Indoor Bike Data notification, when it is decoded, then its flags decide which fields are present. Speed is uint16 in 0.01 km/h, cadence uint16 in 0.5 rpm, power sint16 in W, and heart rate uint8 in bpm.
2. Given the bike reports power, when power is shown, then it is the reported value, not an estimate.
3. Given the bike reports speed, when speed is shown, then it is the reported value.
4. Given a field the flags say is absent, when the readouts show, then that metric falls back to its estimate (L2-022, L2-023) or "—".

---

## L2-022: Speed and distance
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given an Echelon cadence of 80 rpm, when speed is derived, then it is round(80 × 0.37497622, 1) = 30.0 km/h, with banker's rounding.
2. Given each second of a running ride, when distance is updated, then speed in km/h ÷ 3600 is added to it.
3. Given a paused ride, when time passes, then distance does not grow.
4. Given distance, when it is shown, then it has two decimals in km ("2.24 km").

---

## L2-023: Power and energy
**Traces to:** L1-004

The Echelon reports no power, so the app estimates it.

**Acceptance Criteria:**
1. Given an Echelon with cadence 95 and resistance 18, when power is estimated, then it is max(0, round(95 × (0.55 + 18 × 0.155))) = 317 W.
2. Given cadence or resistance is unknown, when power is estimated, then it is unknown and shown as "—".
3. Given a segment with cadence aim 100 and level 18, when target power is computed, then it is 334 W by the same formula.
4. Given average power 208 W after 760 running seconds, when energy is shown, then it is round(208 × 760 ÷ 1000 ÷ 0.24 ÷ 4.184) = 157 kcal.
5. Given each running second, when output is updated, then the second's power ÷ 1000 is added to the ride's output in kJ.

## L2-025: Set resistance command
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given an Echelon and a target resistance of 12, when it is sent, then the bytes `F0 B1 01 0C AE` are written with response. For 32, the bytes are `F0 B1 01 20 C2`.
2. Given a target outside 1 to 32, when it is requested, then it is clamped to that range before it is sent.
3. Given an FTMS bike with control, when a target is sent, then it goes as Set Target Resistance Level, mapped by L2-014 AC4.
4. Given a command, when the bike acknowledges the write, then the time from write to acknowledgement is recorded in milliseconds.

## L2-026: Target resistance and resistance
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a target resistance was sent, when the bike reports a different resistance, then the readout shows the bike's resistance ("6 / of 32"), and the target is the plan's level.
2. Given the bike reports a new resistance, when the readout updates, then it shows the new value within one second.
3. Given no resistance has been reported, when the readout shows, then it reads "—".

## L2-027: Plan-driven resistance
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a running ride that follows a plan, when a segment starts, then its level is sent as the target resistance within 500 ms of the segment boundary.
2. Given Custom ride follows a plan, when the resistance panel shows, then it reads "Following the plan — levels change with each interval."; in flat mode it reads "Holding a flat level for the whole ride."
3. Given a paused ride, when time passes, then no segment changes and no command is sent.
4. Given the bike reconnects mid-segment, when it is back, then the current segment's level is sent again.

## L2-028: Manual resistance
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given a ride with a connected bike, when the rider presses "Raise resistance" or "Lower resistance", then the target resistance moves by one level, clamped to 1 to 32, and is sent.
2. Given Custom ride, when the rider presses one of the 32 "Level N" bars, then the target becomes N. The bar for the current level carries `aria-current="true"`, and bars below it show as on.
3. Given the rider changes the level by hand during a segment, when the next segment starts, then the plan's level applies again.
4. Given no connected bike, when the resistance controls show, then every −, + and level bar is disabled.
5. Given the race and class ride steppers, when they show, then they carry `aria-label` "Resistance {n} of 32" on the readout.

## L2-029: Sent to bike
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given Custom ride, when a target resistance is sent, then a row is added at the top of "Sent to bike" ("5:30 RES 6 · plan · ack 34ms"). It holds the ride time, the level, the source (plan or manual) and the acknowledgement time.
2. Given no bike is connected, when the log shows, then it reads "Nothing sent — no bike connected."
3. Given the log, when it holds more than 50 rows, then the oldest are dropped from view (they stay in the packet log, L2-114).
4. Given the log heading, when it shows, then it names the link ("BLE · 0bf669f1").

## L2-031: Heart-rate strap
**Traces to:** L1-006

_(Mock gap: connecting a strap.)_

**Acceptance Criteria:**
1. Given Profile's Settings, when the rider chooses to connect a heart-rate strap, then the browser chooser opens filtered to the Heart Rate service (`0x180D`).

## L2-168: Opt-in announcer voice pack download and local storage
**Traces to:** L1-028

The race announcer voice pack (~85 MB quantized ONNX text-to-speech model) is opt-in, hosted on Telo Ride's own origin, and stored locally in the browser's Origin Private File System (OPFS).

**Acceptance Criteria:**
1. Given a rider who has not opted in to the race announcer, when Telo Ride loads or a race runs, then zero model bytes are downloaded and no AI worker is started.
2. Given Settings → This device (or the Sound section prompt), when the rider presses "Download voice pack", then Telo Ride fetches the voice pack exclusively from Telo Ride's own origin (`/models/voice-announcer/`), shows live download progress (percentage and MB downloaded of total), and offers "Cancel".
3. Given a download in progress, when the rider presses "Cancel", then the download aborts immediately, all partial files are deleted from OPFS, and the pack status returns to "Not downloaded".
4. Given a completed download, when the pack is stored in OPFS, then Telo Ride requests persistent storage (`navigator.storage.persist()`), displays the pack size on disk (e.g., "Race announcer · 85 MB") with "Delete voice pack", and runs the announcer completely offline on subsequent visits.
5. Given a download fails due to a dropped network or insufficient storage (`QuotaExceededError`), when the failure occurs, then partial files are cleaned up, a plain-language error message explains the cause ("Not enough storage on this device" or "Download interrupted — try again"), and the rest of Telo Ride continues unaffected.
6. Given the rider presses "Delete voice pack", when deletion completes, then the OPFS files are removed, the Race announcer switch turns off, and a toast confirms the freed MB.
7. Given the browser evicts the OPFS voice pack between sessions, when a race opens, then the race starts without error, audio commentary stays silent, visual captions continue if enabled, and Settings shows the pack as "Not downloaded".

## L2-169: Race announcer settings and controls
**Traces to:** L1-028

7. Given any announcer control on Settings, when it is measured, then its touch target is at least 44 × 44 px, it operates by touch and keyboard with a visible focus ring, and its state is conveyed by words and ARIA attributes rather than colour alone.

## L2-170: Race event triggers, priority queue, and accurate callouts
**Traces to:** L1-028

During a race, a deterministic event director translates live race state into concise, factual play-by-play callouts without audio spam.

**Acceptance Criteria:**
1. Given the race announcer is enabled in a race, when any of the following events occur, then the director enqueues a matching callout:
   - **Start countdown & launch:** synchronized callouts on the race start countdown and "GO!";
   - **Position change & overtake:** taking a position, closing within 15 m of a rider ahead, or being overtaken;
   - **Climb & stage transition:** entering a stage whose target resistance rises by 3 or more levels, or cresting that climb;
   - **Stage cadence lock:** holding within ±5 rpm of the stage's target cadence for 30 continuous seconds, or dropping more than 10 rpm below target during an uphill stage;
   - **Personal-best ghost split:** passing or being passed by the ghost, or crossing a stage boundary with a measurable time/metre split;
   - **Final sprint & finish:** entering the final 500 m (or final 30 s) and crossing the finish line with final standing.
2. Given multiple events occur simultaneously, when the director selects the next callout, then it strictly enforces priority order (Finish / Final sprint > Start countdown > Overtake / Ghost pass > Climb transition > Cadence lock) and drops superseded lower-priority events.
3. Given normal racing (excluding Start countdown and Finish), when a callout finishes playing, then the director enforces a minimum 20-second cooldown before playing the next callout.
4. Given a queued callout that has waited more than 5 seconds without starting playback, when the queue is polled, then the stale callout is discarded so commentary never lags behind the race.
5. Given a solo race is paused, when the rider pauses, then active speech stops within 100 ms and queued callouts are cleared; resuming must not replay stale callouts.
6. Given any callout containing a numeric metric (position, gap in metres, target resistance, target cadence), when the callout is composed, then every value must be read directly from the live race store and match the HUD readout at the moment of the event.

## L2-171: Lobby pre-caching and zero-jank audio mixing
**Traces to:** L1-028

Common race phrases are pre-synthesized before racing begins, live synthesis runs off the main thread, and playback mixes cleanly with existing ride audio.

**Acceptance Criteria:**
1. Given the announcer is enabled and the rider enters the Race Lobby (or starts a solo race), when the pre-race countdown runs, then the AI worker pre-synthesizes common static callouts ("3, 2, 1, GO!", "Final sprint!", "Cadence locked!", "You took the lead!") into an in-memory PCM cache bounded to at most 30 clips.
2. Given a dynamic callout (including a rider name, bot name, or metre gap) triggers mid-race, when synthesis runs, then it executes exclusively inside a dedicated Web Worker (`ai.worker`) and never executes neural inference on the Angular main thread.
3. Given an announcer clip plays while World music or Ride sound is active, when playback starts, then Web Audio smoothly ducks World music and Ride sound by 6 to 10 dB over 150 ms and restores their configured levels over 250 ms after speech completes.
4. Given the Race announcer is off, when a race runs, then zero announcer Web Audio nodes, PCM buffers, or worker sessions are allocated.

## L2-173: Performance, memory lifecycle, and thermal auto-governor
**Traces to:** L1-028

The announcer must protect Telo Ride's initial bundle size, 3D frame rate, and multi-hour tablet memory stability.

**Acceptance Criteria:**
1. Given `frontend/` is built for production, when the initial bundle is measured, then the announcer library (`frontend/projects/ai/`) and ONNX runtime are lazy-loaded via dynamic `import()` and add at most 2 KB gzipped (contracts and no-op stubs only) to the initial chunk.
2. Given a 3D race is running at 1920 × 1080 on the reference laptop with the announcer active, when frame rate is measured, then the world holds at least 50 frames per second on average and never drops below 30 fps for more than 1 second (matching L2-136); mid-ride inference must prefer WebNN (NPU) or WASM SIMD (CPU) before WebGPU.
3. Given the browser supports `PressureObserver`, when compute pressure enters `serious` or `critical` during a race, then the announcer automatically pauses live ONNX synthesis (serving only pre-cached clips and visual captions) and resumes live synthesis only after pressure remains `nominal` or `fair` for 30 continuous seconds.
4. Given the announcer is active during a race, when memory is measured, then the PCM clip cache holds at most 30 clips (at most 15 MB total) and the event history ring buffer holds at most 64 entries.
5. Given a rider enters and leaves a race repeatedly (at least 5 consecutive cycles), when the race route is destroyed, then the announcer releases its ONNX session, closes Web Audio nodes, cancels timers, terminates or idles the worker, and returns heap memory to within 10 MB of the pre-race baseline.
6. Given a 3-hour race with the announcer active, when memory is measured from the first minute to the last, then total page memory growth stays within the 50 MB budget of L2-138.

## L2-174: Security, privacy, and input sanitization
**Traces to:** L1-028

The announcer must uphold Telo Ride's zero-exfiltration privacy guarantee and defend against untrusted multiplayer text and corrupted model files.

**Acceptance Criteria:**
1. Given the announcer downloads weights or synthesizes speech, when network traffic is inspected, then requests go exclusively to Telo Ride's own origin (`/models/voice-announcer/...`) under the app's strict CSP (`connect-src 'self'`), and zero audio, telemetry, or display names leave the device.
2. Given an untrusted string (such as another rider's display name from a multiplayer lobby or a course stage title) is interpolated into a callout, when the text is prepared for synthesis and captions, then it must strip HTML/script tags, control characters, and SSML/phoneme markup, and clamp the interpolated name to at most 24 characters.
3. Given a multiplayer display name contains HTML or script payloads (e.g., `<img src=x onerror=alert(1)>`), when the callout banner renders it, then it is rendered strictly as plain text with zero script execution or HTML injection.
4. Given a voice pack download completes, when the files are verified before committing to OPFS, then each file's SHA-256 hash must match the signed/pinned manifest served from Telo Ride's origin; any mismatch must reject and delete the files and surface a generic integrity error code.
