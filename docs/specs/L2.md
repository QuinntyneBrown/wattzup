# L2 - Detailed Requirements

Protocol constants used throughout (taken from the prototype):

| Name | Value |
|---|---|
| Service UUID | `0bf669f1-45f2-11e7-9598-0800200c9a66` |
| Write characteristic | `0bf669f2-45f2-11e7-9598-0800200c9a66` |
| Notify characteristic | `0bf669f4-45f2-11e7-9598-0800200c9a66` |
| Init: device info | `F0 A1 00 91` |
| Init: resistance range | `F0 A3 00 93` |
| Init: start data stream | `F0 B0 01 01 A2` |
| Keepalive | `F0 A0 01 01 92` |
| Set resistance | `F0 B1 01 <level> <checksum>` |
| Checksum | sum of all preceding bytes `& 0xFF` |
| km/h per rpm | `0.37497622` |
| km per mile | `1.609344` |
| Resistance range | 1–32 |

The constants above are the bike's. The treadmill's (L2-062 to L2-074) are in
`docs/protocol/echelon-treadmill-frames.md`. Requirements L2-001 to L2-061 describe the bike; where
the treadmill differs, L2-062 to L2-074 say so and take precedence for the treadmill. Treadmill support is off unless `Wattzup:Treadmill:Enabled` is on (L2-075); L2-062 to L2-074 apply only
while it is on. On the
treadmill the UI calls a ride a *run* and a `flat` plan *Steady*; the API's identifiers (`flat`, the
`workout.status` strings) are the same on both machines.

## L2-001: Bike scanning
**Traces to:** L1-001

The backend must scan for BLE devices for up to 20 seconds per attempt and select the first device whose advertised name starts with `ECH` (case-insensitive) or whose advertised service UUIDs include the Echelon service UUID (case-insensitive).

**Acceptance Criteria:**
1. Given the scanner is running, when a scan starts, then `ble` is `scanning`, `error` is `null`, and the change is broadcast.
2. Given a device advertising the name `ECHEX-3-141844`, when it is discovered, then it is selected.
3. Given a device named `echex-3` (lowercase), when it is discovered, then it is selected.
4. Given a device with no name that advertises the Echelon service UUID in upper case, when it is discovered, then it is selected.
5. Given a device named `Peloton` that does not advertise the Echelon service, when it is discovered, then it is not selected.
6. Given no matching device is found within 20 seconds, when the scan times out, then `ble` stays `scanning`, `error` is `No Echelon bike found yet — pedal to wake it up`, and a new scan starts immediately.

---

## L2-002: Connection and initialisation
**Traces to:** L1-001

On selecting a device, the backend must connect, subscribe to the notify characteristic, then send the three init commands in order with write-with-response, 300 ms apart.

**Acceptance Criteria:**
1. Given a device is selected, when connection starts, then `ble` is `connecting` and `device` is the device name, or its address if it has no name.
2. Given the connection succeeds, when it is established, then `ble` is `connected` and the change is broadcast.
3. Given the connection is established, when initialisation runs, then notifications are subscribed before any init command is written.
4. Given initialisation runs, then the commands device info, resistance range and start data stream are written in that order, each with response, with at least 300 ms between writes.

---

## L2-003: Keepalive
**Traces to:** L1-001

While connected, the backend must write the keepalive command once per second and broadcast state on each keepalive.

**Acceptance Criteria:**
1. Given the bike is connected and initialised, when 5 seconds pass, then between 4 and 6 keepalive writes have been sent, each with response.
2. Given the bike is connected, when a keepalive is sent, then a state broadcast follows so time-derived fields (`displayed_seconds`) stay current.

---

## L2-004: Disconnect and error recovery
**Traces to:** L1-001

The backend must recover automatically from disconnects and from any Bluetooth exception.

**Acceptance Criteria:**
1. Given the bike is connected, when it disconnects, then `ble` becomes `disconnected`, the active bike connection is cleared, and scanning restarts.
2. Given any Bluetooth exception, when it occurs, then `ble` is `error`, `error` is `<ExceptionType>: <message>`, the state is broadcast, and scanning restarts after 3 seconds.
3. Given repeated failures, when the backend has run for 1 hour with the bike off, then the process is still running and still scanning.
4. Given the bike is off, when it is switched on and pedalled, then the backend connects within one scan cycle (≤ 20 s) without restarting.
5. Given `ble` is not `connected` or `connecting`, when `POST /api/bike/reconnect` is called, then the current wait or scan is cancelled, a new scan starts at once, and the response is 202; given `ble` is `connected` or `connecting`, the response is 409 ProblemDetails with `code` = `already_connected`. *(New, for the design's Reconnect button.)*

---

## L2-005: Packet framing and counting
**Traces to:** L1-002

Every notification must be counted and logged; only well-formed packets are decoded.

**Acceptance Criteria:**
1. Given any notification, when it is received, then `packets` increases by 1, even if the packet is later ignored.
2. Given a packet shorter than 4 bytes, when it is received, then no metric changes.
3. Given a packet whose first byte is not `0xF0`, when it is received, then no metric changes.
4. Given a packet of an unknown type (e.g. `F0 D0 01 01 C2`), when it is received, then no metric changes and no error is raised.

---

## L2-006: Resistance packet decoding
**Traces to:** L1-002

A packet with type byte `0xD2` must set `resistance` to byte index 3.

**Acceptance Criteria:**
1. Given packet `F0 D2 01 0C CF`, when it is decoded, then `resistance` is 12.
2. Given a resistance packet is decoded, then `last_data_at` is set to the current time, `first_data_at` is set if it was `null`, and state is broadcast.

---

## L2-007: Workout data decoding
**Traces to:** L1-002

A packet with type byte `0xD1` and at least 13 bytes must set cadence to the big-endian 16-bit value at bytes 9–10, and derive speed from it. `speed_kmh` = round(cadence × 0.37497622, 1). `speed_mph` = round(cadence × 0.37497622 ÷ 1.609344, 1), computed from the unrounded km/h value.

**Acceptance Criteria:**
1. Given packet `F0 D1 09 00 05 00 00 00 00 00 50 00 1F` (bytes 9–10 = `00 50`), when it is decoded, then `cadence` is 80, `speed_kmh` is 30.0 and `speed_mph` is 18.6.
2. Given bytes 9–10 are `01 00`, when decoded, then `cadence` is 256.
3. Given cadence 0, when decoded, then `speed_kmh` and `speed_mph` are both 0.0.
4. Given a `0xD1` packet of 12 bytes, when received, then no metric changes.
5. Given a workout packet is decoded, then `last_data_at`/`first_data_at` are updated as in L2-006 and state is broadcast.

---

## L2-008: Set resistance command
**Traces to:** L1-003

The backend must build the set-resistance command `F0 B1 01 <level> <checksum>` and write it with response.

**Acceptance Criteria:**
1. Given level 12, when the command is built, then the bytes are `F0 B1 01 0C AE`.
2. Given level 32, when the command is built, then the bytes are `F0 B1 01 20 C2`.
3. Given the bike is connected, when a resistance of 12 is sent, then `target_resistance` becomes 12 and state is broadcast.
4. Given the bike is not connected, when a resistance send is attempted, then nothing is written and the send reports failure.

---

## L2-009: Target vs. actual resistance
**Traces to:** L1-003

The state must carry `target_resistance` (last requested) separately from `resistance` (last reported by the bike).

**Acceptance Criteria:**
1. Given `target_resistance` is 20 and the bike still reports 12, when state is read, then `target_resistance` is 20 and `resistance` is 12.
2. Given the bike then reports 20, when state is read, then both are 20.

## L2-010: Workout plan definition and validation
**Traces to:** L1-004

*(Changed: the design's finite plans replace the prototype's list of steps repeated in cycles; see ADR 0002. Changed again: a third kind, `intervals`, makes every set, the warm-up and the cool-down configurable.)* A workout is defined by a plan of one of three kinds, submitted as JSON with snake_case fields:

| Kind | Fields | Allowed values |
|---|---|---|
| `hiit` | `rounds` | integer 1–30 |
| | `work_seconds`, `rest_seconds` | integer 5–3600 |
| | `work_level`, `rest_level` | integer 1–32 |
| | `warmup`, `cooldown` | boolean (a warm-up lasts 180 s, a cool-down 120 s) |
| `flat` | `level` | integer 1–32 |
| | `minutes` | integer 1–180 |
| | `cadence` | integer 40–150 (the rider's cadence goal, rpm) |
| `intervals` | `warmup`, `cooldown` | `null` (off) or `{seconds, level, cadence}`: `seconds` integer 60–1800, `level` 1–32, `cadence` 40–150 (the cadence aim, rpm) |
| | `sets` | array of 1–10 sets, in ride order |
| | set `rounds` | integer 1–30; the rounds of all sets add up to at most 30 |
| | set `work_seconds` | integer 5–3600 |
| | set `rest_seconds` | integer 0 or 5–3600; 0 means the set's efforts have no recover |
| | set `work_level`, `rest_level` | integer 1–32 |
| | set `work_cadence`, `rest_cadence` | integer 40–150 (cadence aims, rpm) |

An `intervals` ride (warm-up, every set's rounds, cool-down) lasts at most 180 minutes.

*(New: video ride-along, L2-076, ADR 0012.)* Every plan kind, on either machine, may carry `video`:

| Field | Allowed values |
|---|---|
| `video` | absent or `null` (no video), or `{url, start_seconds}` |
| `video.url` | a YouTube link: `youtube.com/watch?v=<id>`, `youtu.be/<id>`, `youtube.com/shorts/<id>` or `youtube.com/embed/<id>`, with or without `https://`, `www.` or `m.`, where `<id>` is 11 characters of `A–Z a–z 0–9 _ -`; other query parameters are ignored |
| `video.start_seconds` | number 0–43200 in steps of 0.1: the point in the video that lines up with the ride's 0:00 |

The backend keeps only the video id and the start point; it never fetches the link.

**Acceptance Criteria:**
1. Given `{"kind":"hiit","rounds":8,"work_seconds":40,"rest_seconds":20,"work_level":18,"rest_level":6,"warmup":true,"cooldown":true}`, when submitted, then the plan is accepted.
2. Given `{"kind":"flat","level":12,"minutes":30,"cadence":85}`, when submitted, then the plan is accepted.
3. Given `rounds` 0 or 31, when submitted, then it is rejected with 400 and the field `rounds` is named with the message `Enter 1 to 30 rounds.`
4. Given `rest_seconds` 4, when submitted, then it is rejected with 400 and the field `rest_seconds` is named with the message `Recover must be at least 0:05.`; given `work_seconds` 4, the message is `Work must be at least 0:05.`
5. Given a level of 0 or 33 in any level field, when submitted, then it is rejected with 400 naming that field with `Level must be 1 to 32.`
6. Given `minutes` 0 or 181, when submitted, then it is rejected with 400 naming `minutes` with `Enter 1 to 180 minutes.`; given `cadence` 39 or 151, it names `cadence` with `Cadence goal must be 40 to 150 rpm.`
7. Given an unknown `kind`, a missing field, a non-integer number or a non-boolean switch, when submitted, then it is rejected with 400 and no workout is started; the field is named with `Choose HIIT, Intervals or Flat.` (`kind`), `Enter a whole number.` (a missing or mistyped number) or `Choose on or off.` (a missing or mistyped switch).
8. Given any rejection, then the body is a ProblemDetails with `code` = `invalid_workout` and an `errors` map from field name to messages.
9. Given `work_seconds` or `rest_seconds` over 3600, when submitted, then it is rejected with 400 naming the field with `Work must be at most 60:00.` or `Recover must be at most 60:00.`
10. Given malformed JSON, when submitted, then it is rejected with 400, `code` = `invalid_workout` and `errors` `{"body":["The request body is not valid JSON."]}`.
11. Given `{"kind":"intervals","warmup":{"seconds":300,"level":14,"cadence":80},"sets":[{"rounds":1,"work_seconds":30,"work_level":24,"work_cadence":100,"rest_seconds":180,"rest_level":8,"rest_cadence":72},{"rounds":2,…,"rest_seconds":150,…},{"rounds":2,…,"rest_seconds":120,…},{"rounds":2,…,"rest_seconds":90,…},{"rounds":1,…,"rest_seconds":0,…}],"cooldown":{"seconds":360,"level":6,"cadence":70}}` (every elided field as in the first set; the *Descending recoveries* plan), when submitted, then the plan is accepted; `warmup` or `cooldown` `null` is accepted too.
12. Given an `intervals` plan, then a failing field inside it is named by its path, `warmup.seconds`, `cooldown.level` or `sets[<i>].<field>` with `i` from 0, with these messages: `sets` missing, not an array, empty or longer than 10, `Enter 1 to 10 sets.`; a set's `rounds` outside 1–30, `Enter 1 to 30 rounds.`; `work_seconds` and the levels as criteria 4, 5 and 9; `rest_seconds` 1–4, `Recover must be 0 (none) or at least 0:05.`, over 3600, `Recover must be at most 60:00.`; a cadence aim outside 40–150, `Cadence aim must be 40 to 150 rpm.`; warm-up `seconds` outside 60–1800, `Warm-up must be 1:00 to 30:00.` (`Cool-down must be 1:00 to 30:00.` for the cool-down); `warmup` or `cooldown` neither `null` nor an object, `Choose on or off.`
13. Given an `intervals` plan whose sets' rounds add up to more than 30, then `sets` is named with `At most 30 efforts in a plan.`; given one longer than 180 minutes, then `sets` is named with `A ride can be at most 180 minutes.`
14. Given any valid plan with `"video":{"url":"https://www.youtube.com/watch?v=QUoToFsMNig","start_seconds":12}`, when submitted, then it is accepted and the workout reports `plan.video` `{"video_id":"QUoToFsMNig","start_seconds":12.0}` (L2-014); the same holds for `youtu.be/QUoToFsMNig`, `m.youtube.com/watch?v=QUoToFsMNig&t=40`, `youtube.com/shorts/QUoToFsMNig` and `www.youtube.com/embed/QUoToFsMNig`.
15. Given `video` absent or `null`, when submitted, then it is accepted and the workout reports `plan.video` `null`.
16. Given `video.url` that is not one of those forms (e.g. `https://vimeo.com/76979871`, `https://www.youtube.com/watch?v=short`, `javascript:alert(1)`, or a link over 2048 characters), when submitted, then it is rejected with 400 naming `video.url` with `That doesn't look like a YouTube link.`
17. Given `video.start_seconds` below 0, above 43200 or not a number, when submitted, then it is rejected with 400 naming `video.start_seconds` with `Start point must be 0:00 to 12:00:00.`; a value with more than one decimal place is rounded to 0.1.

## L2-011: Workout execution
**Traces to:** L1-004

*(Changed: the plan is finite; it no longer loops.)* The engine must advance the ride one second at a time while the workout is `running`, tracking `elapsed_seconds` from 0 to `total_seconds` and the current `segment` and its `remaining` seconds.

**Acceptance Criteria:**
1. Given a workout starts, then `workout` holds the plan, its `segments`, `segment` 0, `elapsed_seconds` 0, `total_seconds`, `remaining` equal to segment 0's duration, `mode` `plan`, `summary` (L2-060) and `status`.
2. Given the workout is `running`, when 1 second passes, then `elapsed_seconds` increases by 1, `remaining` decreases by 1, and state is broadcast.
3. Given `remaining` reaches 0 on a segment that is not the last, when the next tick runs, then `segment` increases by 1 and `remaining` is that segment's duration.
4. Given `elapsed_seconds` reaches `total_seconds`, then `status` is `ended`, ticking stops, and the bike is left at the last segment's level.

---

## L2-012: Automatic resistance during workouts
**Traces to:** L1-004

*(Changed from the prototype's per-step resend; the 5-second resend rule is kept.)* While `mode` is `plan`, the engine must set the bike to the current segment's level.

**Acceptance Criteria:**
1. Given a segment starts, when its first tick runs, then the segment's level is sent once with source `plan`.
2. Given the bike reports a resistance different from the level last sent, when `remaining` is a multiple of 5, then that level is sent again.
3. Given the bike reports the level last sent, when ticks run, then no further sends happen for that segment.
4. Given a send fails, then `error` is `set resistance failed: <message>`, the command is logged as `failed` (L2-048), and the workout keeps running.
5. Given the bike reconnects after a pause, when the next tick runs, then the current segment's level is sent again.
6. Given `mode` is `manual` (L2-047), then the engine sends no plan level until the mode returns to `plan`, and the resend of criterion 2 applies to the manual level instead.

---

## L2-013: Waiting, disconnect, shutdown and replacement
**Traces to:** L1-004

*(The 90-second shut-off rule is kept from the prototype.)*

**Acceptance Criteria:**
1. Given a workout starts while the bike is not connected, then `status` is `waiting for bike`, `elapsed_seconds` and `remaining` do not change, and the ride starts at 0:00 as soon as the bike connects.
2. Given the workout is running and the bike disconnects, then `status` is `paused: bike disconnected` and `elapsed_seconds` and `remaining` do not change.
3. Given the bike has been disconnected for more than 90 seconds during a started ride, then `status` is `ended: bike shut off`, `ended_reason` is `bike shut off`, and the workout stops ticking.
4. Given the bike reconnects within 90 seconds, then the workout resumes from the same `segment` and `remaining`, and the segment's level is sent again (L2-012).
5. Given a workout is active, when a new workout is started, then the old one stops and the new one starts at segment 0 with `elapsed_seconds` 0 and fresh ride totals.
6. Given a workout is active, when it is stopped, then `status` is `stopped`, ticking stops, the bike is left at its current level, and state is broadcast.

## L2-014: State model contract
**Traces to:** L1-005

The JSON state must keep the prototype's snake_case field names so the contract is stable across the rewrite, and add the fields the design needs. *(Changed: `workout` now describes a finite plan; `cycle` and `steps` are removed; the fields from `adapter` on are new.)*

| Field | Type | Notes |
|---|---|---|
| `ble` | string | `starting` \| `scanning` \| `connecting` \| `connected` \| `disconnected` \| `error` |
| `device` | string \| null | advertised name, or address if it has none |
| `device_label` | string \| null | the configured display name of the chosen machine (`Wattzup:Bike:DisplayName`, or `Wattzup:Treadmill:DisplayName`, default `Echelon Stride`), else `device` |
| `error` | string \| null | |
| `resistance` | int \| null | last reported by the bike |
| `target_resistance` | int \| null | last requested |
| `workout` | object \| null | see below |
| `cadence` | int \| null | rpm |
| `speed_kmh` | number \| null | 1 decimal |
| `speed_mph` | number \| null | 1 decimal |
| `packets` | int | |
| `first_data_at` | number \| null | Unix epoch seconds |
| `last_data_at` | number \| null | Unix epoch seconds |
| `ui_clients` | int | |
| `displayed_since` | number \| null | Unix epoch seconds |
| `displayed_seconds` | number | 1 decimal |
| `adapter` | string | `unknown` \| `on` \| `off` |
| `transport` | string | e.g. `CoreBluetooth`, `BlueZ`, `WinRT`, `Simulated` |
| `simulated` | bool | true when started with `--simulate` |
| `exposed` | bool | true when bound to a non-loopback address |
| `bind_address` | string | e.g. `127.0.0.1:8787` |
| `connection_id` | string | first 8 hex digits of the service UUID, `0bf669f1` |
| `power` | int \| null | estimated watts (L2-049) |
| `target_power` | int \| null | estimated target watts for the current segment |
| `avg_power` | int \| null | ride average, watts |
| `distance_km` | number \| null | ride distance, 2 decimals |
| `kcal` | int \| null | ride energy, estimated (L2-049 on the bike, L2-064 on the treadmill) |
| `climb_m` | int \| null | treadmill only: metres climbed this ride (L2-064) |
| `heart_rate` | int \| null | always `null`; no heart-rate source exists (ADR 0003) |

| `target_speed` | number \| null | treadmill only: last requested speed, km/h, 1 decimal (L2-065) |
| `incline` | int \| null | treadmill only: last reported incline, % (L2-064) |
| `target_incline` | int \| null | treadmill only: last requested incline, % (L2-065) |
| `belt` | string \| null | treadmill only: `stopped` \| `starting` \| `running`; `null` on the bike or while the treadmill is not connected (L2-066) |
| `belt_countdown` | int \| null | treadmill only: 3, 2 or 1 during the countdown before the belt starts, else `null` (L2-066) |
| `treadmill_enabled` | bool | true when `Wattzup:Treadmill:Enabled` is on (L2-075) |
| `nearby` | array | Echelon machines heard advertising in the last 30 s, `[{machine, name, label, rssi, signal, seen_at}]`, at most one per machine (L2-074) |
| `ts` | number | stream messages only; Unix epoch seconds |

`workout` is `{plan, summary, segments:[{kind, start, duration, level, cadence, round, speed, incline}], segment:int, remaining:int, elapsed_seconds:int, total_seconds:int, mode:"plan"|"manual", plan_level:int|null, status:string, ended_reason:string|null, session_id:string|null}`. `session_id` is the id of the session the ride was saved as (L2-081), set once the ride has ended on the bike and been saved, else `null`. `status` is one of `waiting for bike`, `starting belt`, `running`, `paused`, `paused: bike disconnected`, `paused: belt stopped`, `ended`, `ended: bike shut off`, `stopped`. The status strings are contract identifiers and are the same on both machines; the UI words them for the chosen machine (L2-071). On the treadmill, `speed_kmh` and `speed_mph` carry the speed the treadmill reports and `distance_km` the ride distance (L2-064); the bike-only fields `resistance`, `target_resistance`, `cadence`, `power`, `target_power`, `avg_power` and `kcal`, the segments' `level` and `cadence` and `plan_level` are `null`; on the bike, the treadmill-only fields and the segments' `speed` and `incline` are `null` (L2-070). Each command entry is `{at, ride_seconds, level, source, status, ack_ms, command, value}` (L2-065). `workout.plan` is the submitted plan with `video` reported as `{video_id:string, start_seconds:number}` or `null`, never the submitted link (L2-010, L2-076). `plan` is the validated plan (L2-010) with `video` `{video_id, start_seconds}` for a ride-along video, else `null` (ADR 0012).

**Acceptance Criteria:**
1. Given the backend has just started, when `GET /api/status` is called, then the response is 200 with `ble` = `starting`, `packets` = 0, `displayed_seconds` = 0, `commands` = `[]`, `nearby` = `[]`, `adapter` = `unknown`, and all nullable fields `null`.
2. Given any state, when it is serialised, then every field above is present with the stated name and type, and nulls are written as `null` rather than left out.
3. Given an exported OpenAPI document, when it is generated, then it describes every endpoint and the state schema.

## L2-015: Event stream
**Traces to:** L1-005

`GET /api/events` must return a Server-Sent Events stream (`text/event-stream`, `Cache-Control: no-cache`).

**Acceptance Criteria:**
1. Given a client connects, then it receives the current state (with `ts`) as its first `data:` message immediately.
2. Given state changes, when a broadcast happens, then every connected client receives one `data:` message with the full state JSON.
3. Given no messages for 15 seconds, when the interval passes, then the client receives a `: ping` comment line.
4. Given a client connects or disconnects, then `ui_clients` equals the number of open streams.
5. Given a client is slow and has 50 undelivered messages, when another broadcast happens, then that message is dropped for that client only and other clients are unaffected.
6. Given a client disconnects abruptly, then its resources are freed and no exception reaches the logs above Debug level.

---

## L2-016: Resistance endpoint
**Traces to:** L1-005

`POST /api/resistance` with body `{"level": <int>}`.

**Acceptance Criteria:**
1. Given the bike is connected and level 12, when called, then the response is 200 `{"sent":12}`.
2. Given level 0, 33, a non-integer or a missing body, when called, then the response is 400 with `{"error":"level must be 1-32"}` (or a ProblemDetails body carrying the same message).
3. Given the bike is not connected, when called with a valid level, then the response is 503 `{"error":"bike not connected"}`.

## L2-017: Workout endpoints
**Traces to:** L1-005

*(Changed for finite plans.)* `POST /api/workout` with a plan body (L2-010), `POST /api/workout/stop`, `POST /api/workout/pause`, `POST /api/workout/resume`, `POST /api/workout/back-to-plan`, and `GET /api/workout/trace`.

**Acceptance Criteria:**
1. Given a valid plan, when `POST /api/workout` is called, then the response is 200 `{"started": <workout>}` and the workout starts, whether or not the bike is connected (L2-013).
2. Given an invalid plan, when called, then the response is 400 as in L2-010.
3. Given any state, when `POST /api/workout/stop` is called, then the response is 200 `{"stopped":true}`.
4. Given no workout exists, when stop is called, then the response is still 200 and `workout` stays `null`.
5. Given pause, resume or back-to-plan is called with no active workout, then the response is 409 ProblemDetails with `code` = `no_active_workout`.

## L2-018: Connection status line
**Traces to:** L1-006

*(Changed: the design's status line replaces the coloured pill.)* The app bar must show an icon, a name and a state label for the connection.

| Condition | Name | State | Icon |
|---|---|---|---|
| `ble` `connected` | `device_label` | `Connected` | bluetooth |
| `ble` `scanning` or `starting` | `Echelon bike` | `Scanning…` | bluetooth, animated unless reduced motion |
| `ble` `connecting` | `device_label` | `Connecting…` | bluetooth |
| `ble` `disconnected` | `device_label` or `Echelon bike` | `Disconnected` | bluetooth-off |
| `adapter` `off` | `Bluetooth` | `Off` | bluetooth-off |
| `ble` `error`, adapter not off | `Bike status` | `Error` | bluetooth-off |
| event stream failed | `Server offline` | `Retrying…` | wifi-off |
| no state yet, or `GET /api/status` failed | `Bike status` | `Unknown` | bluetooth |

**Acceptance Criteria:**

## L2-036: Input validation and hardening
**Traces to:** L1-009

**Acceptance Criteria:**

## L2-045: Plan expansion into segments
**Traces to:** L1-004

*(Changed: work efforts aim at 100 rpm; `intervals` plans expand too.)* The backend must expand an accepted plan into an ordered list of segments `{kind, start, duration, level, cadence, round}`, where `start` is the second offset from the start of the ride and `round` is `null` outside work and recover segments.

**Acceptance Criteria:**
1. Given a `flat` plan with level 12, 30 minutes and cadence 85, when expanded, then there is one segment `{kind:"steady", start:0, duration:1800, level:12, cadence:85, round:null}`.

3. Given a `hiit` plan, when expanded, then each round r (1…`rounds`) is a `work` segment (`work_seconds`, `work_level`, cadence aim 100, round r) followed by a `rest` segment (`rest_seconds`, `rest_level`, cadence aim 72, round r).

5. Given the plan 8 × 40 s / 20 s, work 18, recover 6, warm-up and cool-down, when expanded, then the total duration is 760 s (12:40) and there are 17 segments.

7. 9. Given the *Descending recoveries* plan (L2-010 criterion 11), when expanded, then there are 17 segments, 8 of them `work`, and the total duration is 1800 s (30:00).

## L2-063: Treadmill scanning and connection
**Traces to:** L1-013

*(New.)* With the treadmill chosen, the backend must scan as in L2-001 and select the first device whose advertised name starts with `STRIDE` (case-insensitive), or that advertises the treadmill's service `0bf669f0-45f2-11e7-9598-0800200c9a66` and whose name does not start with `ECH`. It then connects, subscribes to both notify characteristics (`0bf669f3-…` and `0bf669f4-…`), and writes the treadmill's three init commands `F0 A4 00 94`, `F0 A1 00 91` and `F0 A3 00 93` in that order, with response, 300 ms apart. It never writes the bike's start-data-stream command `F0 B0 01 01 A2` at init, because on the treadmill those bytes start the belt (L2-066).

**Acceptance Criteria:**
1. Given the treadmill is chosen and a device named `STRIDE-8s22-000766` is discovered, then it is selected; given it is named `stride-8s` (lower case), it is selected.
2. Given the treadmill is chosen and a device with no name advertises `0BF669F0-45F2-11E7-9598-0800200C9A66`, then it is selected.
3. Given the treadmill is chosen and a device named `ECHEX-3-141844` is discovered, then it is not selected, even if it advertises the treadmill's service.
4. Given the bike is chosen and a device named `STRIDE-8s22-000766` is discovered, then it is not selected, even if it advertises the Echelon service; L2-001's other cases are unchanged.
5. Given the treadmill is selected and connected, when initialisation runs, then both notify characteristics are subscribed before any init command is written, and the init commands are written in the order above, each with response, at least 300 ms apart; `F0 B0 01 01 A2` is not written.
6. Given the treadmill is connected and initialised, then a keepalive `F0 A0 01 <n> <checksum>` is written with response once per second, where `<n>` counts 1, 2, … 255 and then starts again at 1, and state is broadcast on each keepalive (as L2-003).
7. Given the treadmill sends a `0xD0`, `0xD2` or `0xD3` frame, then Wattzup writes the same bytes back to the write characteristic without response, as the treadmill's acknowledgement.
8. Given the treadmill is chosen and no treadmill is found within 20 seconds, then `error` is `No Echelon treadmill found yet — switch it on to wake it up` and a new scan starts at once.
9. Given the treadmill disconnects or a Bluetooth exception occurs, then recovery follows L2-004.
10. Given any treadmill connection, then Wattzup writes only to the write characteristic `0bf669f2-…`, never to any other characteristic, and in particular never to the Device Firmware Update service `FE59`.

## L2-064: Treadmill telemetry decoding
**Traces to:** L1-013

*(New.)* With the treadmill chosen, notifications are counted and logged as in L2-005 and L2-030 and decoded as follows. A `0xD3` frame of at least 6 bytes carries the speed: the big-endian 16-bit value at bytes 3–4 is metres per hour, so `speed_kmh` = round(value ÷ 1000, 1) and `speed_mph` = round(value ÷ 1000 ÷ 1.609344, 1) from the unrounded km/h value, both with banker's rounding. A `0xD2` frame sets `incline` to byte 3 (%). A `0xD0` frame changes no metric. The bike's `0xD1` frame is not decoded on the treadmill.

**Acceptance Criteria:**
1. Given packet `F0 D3 02 23 28 10`, when it is decoded, then `speed_kmh` is 9.0 and `speed_mph` is 5.6.
2. Given packet `F0 D3 02 00 00 C5`, when it is decoded, then `speed_kmh` and `speed_mph` are 0.0.
3. Given packet `F0 D3 02 1B 58 38`, when it is decoded, then `speed_kmh` is 7.0.
4. Given packet `F0 D2 01 05 C8`, when it is decoded, then `incline` is 5; it does not change `resistance`.
5. Given a `0xD3` packet of 5 bytes, a `0xD2` packet of 3 bytes or packet `F0 D0 01 00 C1`, then no metric changes and no error is raised.
6. Given a speed or incline packet is decoded, then `last_data_at` and `first_data_at` are updated as in L2-006 and state is broadcast.
7. Given the reported speed is above 0, then `belt` is `running`; given it is 0, then `belt` is `stopped`, except while `belt` is `starting`, when it stays `starting` (L2-066).
8. Given the treadmill connects, then `belt` is `stopped` until a speed packet says otherwise; given it is not connected, then `belt` is `null`.
9. Given a running workout on the treadmill, then each running tick adds `speed_kmh` ÷ 3600 to `distance_km` (as L2-049 criterion 4), and `power`, `target_power` and `avg_power` stay `null` (ADR 0003's power estimate is bike-only).
10. Given a running workout on the treadmill, then each running tick adds `speed_kmh` ÷ 3600 × 1000 × `incline` ÷ 100 metres to the ride's climb, and `climb_m` is that climb rounded to a whole metre; e.g. 60 ticks at 13.0 km/h and 2 % add 4.33 m.
11. Given a running workout on the treadmill, then each running tick adds an energy estimate to the ride's energy, and `kcal` is that energy rounded to a whole number. The estimate follows the ACSM walking and running equations for a 75 kg runner: with v = `speed_kmh` × 1000 ÷ 60 (m/min) and g = `incline` ÷ 100, VO2 = 0.1·v + 1.8·v·g + 3.5 below 6.5 km/h and 0.2·v + 0.9·v·g + 3.5 from 6.5 km/h, and kcal per second = VO2 × 75 × 5 ÷ 1000 ÷ 60. E.g. one tick at 13.0 km/h and 2 % adds 0.3171 kcal; 60 ticks add 19.0 kcal.
12. Given a new treadmill workout starts, then `distance_km`, `climb_m` and `kcal` reset to 0; given a workout ends or stops, they keep their final values (as L2-049 criterion 6).

## L2-065: Speed and incline commands
**Traces to:** L1-013

*(New.)* The backend must build the set-speed command `F0 B2 02 <hi> <lo> <checksum>`, where `<hi> <lo>` is round(km/h × 1000) as a big-endian 16-bit value, and the set-incline command `F0 B1 01 <incline> <checksum>`, with the checksum of the frame reference, and write each with response. Speed is 0.8 to 19.3 km/h (the Echelon Stride's range, 0.5 to 12 mph) in steps of 0.1; incline is a whole number from 0 to 10 %. Every speed and incline command is logged in `commands` as in L2-048, with `command` `speed` or `incline`, `value` the requested value and `level` `null`; a bike resistance entry has `command` `resistance` and `value` equal to its `level`.

**Acceptance Criteria:**
1. Given speed 9.0, when the command is built, then the bytes are `F0 B2 02 23 28 EF`; given 7.0, `F0 B2 02 1B 58 17`; given 1.0, `F0 B2 02 03 E8 8F`; given 0.8, `F0 B2 02 03 20 C7`; given 19.3, `F0 B2 02 4B 64 53`.
2. Given incline 0, when the command is built, then the bytes are `F0 B1 01 00 A2`; given 5, `F0 B1 01 05 A7`; given 10, `F0 B1 01 0A AC`.
3. Given a speed below 0.8 or above 19.3, or an incline below 0 or above 10, when a command is built, then it is refused and nothing is written.
4. Given the treadmill is connected, when speed 9.0 is sent, then `target_speed` becomes 9.0, an entry `{command:"speed", value:9.0, level:null, status:"sending"}` is added to `commands`, and state is broadcast; when the treadmill then reports 9.0, the entry's `status` becomes `ack` with `ack_ms`.
5. Given the treadmill is connected, when incline 5 is sent, then `target_incline` becomes 5 and an `incline` entry is logged; when the treadmill reports incline 5, it is acknowledged.
6. Given a newer speed entry for a different value, then an older `sending` speed entry is not acknowledged by the newer value (as L2-048 criterion 4); a speed report never acknowledges an incline entry, nor the reverse.
7. Given the treadmill is not connected, when a send is attempted, then nothing is written, the entry is `failed`, and the send reports failure.

## L2-066: Belt control
**Traces to:** L1-013

*(New.)* Wattzup starts the treadmill's belt only to start or resume a workout, and only after a 3-second countdown the UI shows and announces. The start-belt command is `F0 B0 01 01 A2` and the stop-belt command `F0 B0 01 00 A1`, both written with response. Wattzup stops the belt whenever a workout on the treadmill pauses, is stopped, is replaced or ends. *(Changed: the Run Dashboard design.)* When the Bluetooth link drops, the treadmill stops its own belt, so the UI tells the runner to step onto the side rails (L2-071); this is checked on hardware by L2-043 criterion 5. The treadmill's safety key and stop button always stop the belt too, and Wattzup reports either as the belt stopping (criterion 7).

**Acceptance Criteria:**
1. Given the treadmill is connected, when a workout starts or a paused workout resumes and `belt` is not `running`, then `workout.status` is `starting belt`, `belt` is `starting`, `belt_countdown` is 3, and it becomes 2 and 1 on later ticks, each number showing for at least 1 second; `elapsed_seconds` and `remaining` do not change.
2. Given `belt_countdown` is 1, when the next tick runs, then the start-belt command is written, `belt_countdown` is `null`, and `belt` stays `starting` until the treadmill reports a speed above 0.
3. Given `belt` is `starting` after the start-belt command, when the treadmill reports a speed above 0, then `belt` is `running`, `workout.status` is `running`, the current segment's speed and incline are sent (L2-068), and ticking starts.
4. Given the start-belt command was written and the treadmill has not reported a speed above 0 within 10 seconds, then the start-belt command is not repeated, the stop-belt command is written (so a late start cannot move the belt while the ride is paused), `belt` is `stopped`, `workout.status` is `paused: belt stopped`, and `error` is `The belt did not start.`
5. Given a paused workout resumes while `belt` is already `running`, then no countdown runs and the ride continues at once.
6. Given a workout on the treadmill, when it is paused, stopped (`POST /api/workout/stop`), replaced by a new workout, or reaches its end, then the stop-belt command is written once, with response, if the treadmill is connected; `target_speed` keeps its last value.
7. Given a workout is `running` and `belt` is `running`, when the treadmill reports speed 0 (the belt was stopped from the console or the safety key was pulled), then `workout.status` becomes `paused: belt stopped` on the next tick, ticking stops, and Wattzup does not start the belt again by itself; `POST /api/workout/resume` restarts it through the countdown of criterion 1.
8. Given a workout on the treadmill and the treadmill disconnects, then `workout.status` is `paused: bike disconnected` and the 90-second shut-off rule of L2-013 applies; given the treadmill reconnects within 90 seconds, then the workout stays paused (`paused`, as if the rider had paused it) until the rider resumes it, and the belt is started only through the countdown of criterion 1. A disconnect during the countdown cancels it.
9. Given a workout starts on the treadmill while it is not connected, then `status` is `waiting for bike` (L2-013); when the treadmill connects, the countdown of criterion 1 starts.
10. Given the bike is the chosen machine, then no belt command is ever written and `belt` and `belt_countdown` are `null`.
11. Given each belt command, then it is logged through `ILogger` at Information level with the reason (`start`, `pause`, `stop`, `replace`, `end`, `timeout`).

## L2-077: Class catalogue
**Traces to:** L1-014

*(New: from the 2026-11-17 Magic Patterns frames Video Library and Video Workout; ADR 0014.)* A class is a bike plan with the YouTube video it follows. The catalogue of classes is a JSON file the backend reads; nothing in the code lists a class. The setting `Wattzup:Classes:Path` (environment `WATTZUP__CLASSES__PATH`), default `classes.json`, names the file; a relative path resolves against the content root. Wattzup ships a default `classes.json` with the six classes of the mocks (`docs/mocks/README.md`, *Class library*) and one class for each indoor training session in the GCN Training channel's workout playlists, each with its video, on shelves by length (`15-min` to `60-min`). A GCN class's levels follow the video's effort scale: effort *e*/10 is level 8 + 1.6 × *e*, rounded (1/10 is level 10, 10/10 is level 24).

| Field | Rule |
|---|---|
| `shelves` | array of 0–20 `{id, title, tagline}`, in display order |
| `classes` | array of 0–200 `{id, title, channel, focus, description, shelf, plan}`, in display order |
| `id` (shelf and class) | 1–64 characters of `a–z 0–9 -`, unique among the shelves or among the classes |
| `title` | 1–80 characters |
| `channel`, `focus` | 1–40 characters (`GCN Training`, `HIIT`) |
| `tagline`, `description` | 0–280 characters |
| `shelf` | the `id` of a shelf in the file |
| `plan` | a bike plan as L2-010 (`hiit`, `intervals` or `flat` with a level), optionally with `video` `{url, start_seconds}` |

**Acceptance Criteria:**
1. Given a catalogue file of valid shelves and classes, when the backend starts, then every shelf and class is served by L2-078 in file order.
2. Given no `Wattzup:Classes:Path` setting, then the backend reads `classes.json` from the content root; given a path, it reads that file.
3. Given a class whose `plan` L2-010 rejects, whose plan is a treadmill plan (L2-067), whose `shelf` names no shelf, whose `id` repeats an earlier class's, or with a field outside the table, then that class is left out, the others are kept, and a warning is logged naming the class `id` (or its position when it has none) and the field.
4. Given a shelf with an invalid or repeated `id`, then the shelf and the classes on it are left out with a warning naming the shelf.
5. Given the file is missing, unreadable, larger than 1 MB or not valid JSON, then the catalogue is empty, an error naming the path and the reason is logged once, and the backend starts as usual.
6. Given the file has more than 20 shelves or 200 classes, then the first 20 shelves and the first 200 valid classes are kept and a warning names how many were dropped.
7. Given the backend is running, when the file is changed and saved, then within 2 s L2-078 serves the new catalogue, and a ride in progress is not affected; given the new file is invalid as a whole (criterion 5), then the last valid catalogue is kept and the error is logged.
8. Given a class's `plan.video`, then only its video id and start point are kept, as L2-010 criterion 14; the backend never fetches the link or the video.
9. Given any text field, then it is stored and served as plain text; the frontend renders it as text, never as HTML (L2-036).

## L2-081: Session record
**Traces to:** L1-015

*(New: from the Magic Patterns frames Ride Dashboard (`End` builds a session record) and Session Summary, and the rules of the OS file `shared/sessions.ts`; ADR 0015.)* A *session* is a saved ride. When a workout ends on the bike, `Wattzup.Core` builds the session from the samples the workout engine took each running second (power and cadence as the bike reported them, a missing value counting as 0) and saves it (L2-082). Heart rate is not recorded: Wattzup has no heart-rate sensor (ADR 0003).

A session is `{id, ended_at, class_id, title, plan, segments, planned_seconds, ridden_seconds, completed, avg_power, max_power, best_minute_power, avg_cadence, distance_km, kcal, on_target_pct, dips:[{start, duration, target, low, kind, round}], power_trace, cadence_trace}`:

| Field | Rule |
|---|---|
| `id` | 12 characters of `a–f 0–9`, unique among the sessions |
| `ended_at` | the UTC time the workout ended (ISO 8601) |
| `class_id`, `title` | the class's `id` and `title` when the ride was started with `class_id` (criterion 7); otherwise `null` and `workout.summary` (L2-060) |
| `plan`, `segments` | `workout.plan` and `workout.segments` as L2-014 carries them |
| `planned_seconds`, `ridden_seconds` | the plan's total and the running seconds ridden (`elapsed_seconds`) |
| `completed` | `ridden_seconds ≥ planned_seconds − 5` |
| `avg_power`, `max_power` | the mean and the highest estimated power of the running seconds, W, whole (ADR 0003); `avg_power` equals the dashboard's `avg_power` at the end |
| `best_minute_power` | the highest mean of 60 consecutive running seconds of power, W, whole |
| `avg_cadence` | the mean cadence of the running seconds, rpm, whole |
| `distance_km`, `kcal` | the ride's `distance_km` (2 decimals) and `kcal` at the end (L2-049) |
| `on_target_pct` | of the seconds in counted segments (table below), the share not under target, 0–100 whole; 100 when no segment counts |
| `dips` | every run of at least 6 consecutive seconds under target within one counted segment: `start` (ride second), `duration` (s), `target` (the segment's cadence aim), `low` (the lowest cadence in it), `kind` and `round` of the segment |
| `power_trace`, `cadence_trace` | means of each 5 running seconds, whole, oldest first; the last holds the remaining 1–5 seconds |

A second is *under target* when its cadence is below the segment's cadence aim by more than the segment kind's tolerance:

| Segment kind | Counted | Under target when cadence < |
|---|---|---|
| `warmup` | no | — |
| `cooldown` | no | — |
| `work` | yes | aim − 6 rpm |
| `steady` | yes | aim − 6 rpm |
| `rest` | yes | aim − 12 rpm |

**Acceptance Criteria:**
1. Given a workout on the bike with at least 60 running seconds, when it is stopped (`POST /api/workout/stop`, L2-013), when it ends at the end of its plan (`ended`) or when the bike has been off for 90 s (`ended: bike shut off`, L2-058), then one session is saved with the fields of the table, and `workout.session_id` (L2-014) is its `id`.
2. Given a workout with fewer than 60 running seconds, or no workout, when the workout is stopped or ends, then no session is saved and `workout.session_id` stays `null`.
3. Given the treadmill is the machine (L2-062), then no session is ever saved (L1-015).
4. Given a ride ends `completed` false, then the session keeps the ridden part only: the traces, dips and averages cover `ridden_seconds`, and `planned_seconds` is the whole plan.
5. Given each row of the two tables, then the session's `on_target_pct`, `dips`, `best_minute_power` and `completed` follow it, each row proven by a unit test (`Wattzup.Core.Tests`).
6. Given a run under target that spans two segments, then it is two dips, one per segment, each kept only if it lasts at least 6 s.
7. Given `POST /api/workout` (L2-010) with an optional `class_id` beside the plan, then a `class_id` that names a class in the catalogue (L2-077) is kept for the session with that class's `title`; one that names no class answers 400 ProblemDetails with `code` `invalid_workout` and the field `class_id`; without it the session has `class_id` `null`.
8. Given `POST /api/workout/stop` answers, then the body is `{stopped:true, session_id}` with the saved session's `id`, or `null` when none was saved.
9. Given a session, then it holds no heart rate, no Bluetooth device name and no API key or token.

## L2-082: Session storage
**Traces to:** L1-015

*(New: ADR 0015.)* Sessions are kept in one JSON file, `{"sessions":[<session>…]}`, newest first. The setting `Wattzup:Sessions:Path` (environment `WATTZUP__SESSIONS__PATH`), default `sessions.json`, names the file; a relative path resolves against the content root.

**Acceptance Criteria:**
1. Given no `Wattzup:Sessions:Path` setting, then the backend reads and writes `sessions.json` in the content root; given a path, it reads and writes that file.
2. Given a valid sessions file, when the backend starts, then every session in it is served by L2-083; given the backend is restarted after a session was saved, then the session is still served.
3. Given a session is saved, then the file is written whole to a temporary file in the same folder and moved over the old one, so a crash during the write leaves either the old file or the new one, never a partial file.
4. Given more than 500 sessions, then the 500 newest are kept and the oldest are dropped from the file.
5. Given the file is missing at start, then the backend starts with no sessions and creates the file on the first save.
6. Given the file is not valid JSON, is not a sessions file or is larger than 16 MB at start, then it is renamed to `<file>.unreadable` (replacing an older one), an error naming the path and the reason is logged once, and the backend starts with no sessions; the old history is never overwritten unread.
7. Given the file cannot be written (permission, disk full), then an error is logged, the session is still served until the backend stops, and ending the ride is not delayed or refused.
8. Given an automated test, then the file is in a per-test temporary folder; no test reads or writes the content root's `sessions.json`.

## L2-083: Sessions API
**Traces to:** L1-005

*(New: ADR 0015.)* Three read-only endpoints serve the sessions (L2-081) and the figures of L2-087. A session *summary* is `{id, ended_at, class_id, title, ridden_seconds, planned_seconds, completed, avg_power, on_target_pct, dip_count}`.

**Acceptance Criteria:**

## L2-087: Streaks, weekly goal, previous attempt, bests and achievements
**Traces to:** L1-015

*(New: from the rules of the OS file `shared/sessions.ts`; ADR 0015.)* `Wattzup.Core` computes these from the saved sessions and the time now (`TimeProvider`), in the local time zone of the machine next to the bike. A *ridden day* is a local date on which a session ended. A *finished attempt* at a class is a `completed` session with that `class_id`; rides from `/setup` (`class_id` `null`) have no attempts, no previous attempt and no class best.

| Figure | Rule |
|---|---|
| `streak.rode_today` | today is a ridden day |
| `streak.current` | the number of consecutive ridden days ending today when `rode_today`, else ending yesterday (a streak survives until the end of today); 0 when that day was not ridden |
| `streak.best` | the longest run of consecutive ridden days ever, and never less than `current` |
| `week.rides` | the sessions that ended since Monday 00:00 of this week (local); a week starts on Monday |
| `week.goal` | 4 |
| previous attempt | the latest finished attempt at the same class that ended before this session; none for `class_id` `null` |

| Best (in this order) | Set when |
|---|---|
| `Best 1-minute power` | at least one session ended before this one, and `best_minute_power` is higher than every earlier session's |
| `Best average on this class` | this session is a finished attempt, an earlier finished attempt at the class exists, and `avg_power` is higher than every earlier one's |
| `No cadence dips` | this session is `completed`, has at least one `work` segment and has no dips |

| Achievement `id` | Title | Detail | Value | Goal | Unit |
|---|---|---|---|---|---|
| `seven-straight` | Seven straight | Ride seven days in a row | `streak.best` | 7 | days |
| `century` | Century | Ride 100 km in total | the sum of `distance_km` | 100 | km |
| `long-hour` | The long hour | Finish five rides of an hour or more | completed sessions with `planned_seconds` ≥ 3600 | 5 | — |
| `interval-regular` | Interval regular | Finish eight interval rides | completed sessions whose plan is `hiit` or `intervals` | 8 | — |
| `metronome` | Metronome | Hold cadence target 97% of a ride | the highest `on_target_pct` of a completed session | 97 | % |
| `clean-sheet` | Clean sheet | Finish an interval ride with no cadence dips | completed sessions with a `work` segment and no dips | 1 | — |

The design's *Ladder regular* (a named class) and the 60-minute tier of *The long hour* are expressed by plan properties, because nothing in the code names a class (ADR 0014).

**Acceptance Criteria:**
1. Given each row of the three tables, then the figure follows it, proven by a unit test per row (`Wattzup.Core.Tests`) with the time set by `FakeTimeProvider`, including: a session at 23:59 and one at 00:01 the next local day are two ridden days; ridden yesterday but not today keeps the streak; last ridden two days ago gives 0; two sessions on one day count one day but two rides this week; a session on Sunday is not in the week that starts on Monday.
2. Given an achievement, then `unlocked` is `value ≥ goal`, and the list is ordered unlocked first, then by `value ÷ goal` descending, then by the table's order.
3. Given no sessions, then `streak` is `{current:0, best:0, rode_today:false}`, `week.rides` 0, `totals` zero, `classes` `[]`, and every achievement has value 0 and is locked.
4. Given the figures, then none is ever invented: with no earlier session there is no previous attempt and no `Best 1-minute power`.
