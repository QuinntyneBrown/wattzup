Skeleton

A grey stand-in shaped like what is coming. Telo Ride does not need one today; here is when it would.

Overview

A skeleton is a grey stand-in shaped like the content that is about to appear. The kit has .skeleton (a raised block that pulses), and this page adds shapes and composed card and row skeletons. No screen in Telo Ride uses one today, and that is deliberate. The mocks manifest marks loading as not_applicable on 14 of its 17 screens, with the same reason each time:

"The design draws no loading state: every screen reads local, synchronous data (shared/game.ts, shared/videoWorkouts.ts), so there is nothing to wait for."

Maps, classes, riders, bots and your progress are bundled with the app and read from the device. The three screens without that reason (Diagnostics, End ride, Feedback) wait on Bluetooth or a send, and they use a spinner or a busy button instead, because the wait is about one action, not a layout. The rule below is for the day data comes from a network.

The rule

  1. Do not add a loading state for local data. Draw the screen.
  2. When data comes over the network and the wait may pass about 300 ms, draw a skeleton of the real layout: same grid, same sizes, no text.
  3. Show it only after 300 ms (shorter waits flash), and swap the whole region at once when the data lands.
  4. After about 10 s, replace it with an error or an empty state that says what happened.
  5. Waits tied to one action (pairing, saving) use a spinner, not a skeleton.

Anatomy

  1. Cover.skeleton--rect at the cover's ratio (16:9).
  2. Title line.skeleton--text, 16px tall, 70% wide.
  3. Meta line.skeleton--text, 12px tall, 50% wide.

Shapes

Title, text, circle, numeral, button; widths from --skeleton-width.

Sizes

Skeletons have no sizes of their own: each shape copies the size of the element it stands in for (a 12px line for 12px text, the cover ratio for a cover).

States

A skeleton has no hover, focus, active or disabled state: it is not interactive and never takes focus. Its states are the region's: loading, loaded, empty and error. The default, hover, focus, active and disabled columns do not apply.

Both themes

The fill is --color-raised on the canvas and on panels. Skeletons are decoration; they have no contrast requirement, but they must be visible against the surface (raised on panel is about 1.2:1 in both themes, enough to read as a shape).

Responsive behaviour

  • A skeleton uses the real layout's grid, so it reflows exactly as the content will: one class card per row at 360px, two at 640px, three or four at 1024px.
  • Show the number of items a screen usually holds at that width (three rows, one row of cards), not a full page.

Theming

.skeleton { background: var(--color-raised); animation: skeleton-pulse var(--duration-pulse) var(--ease-standard) infinite; }
.skeleton-panel .skeleton { background: var(--color-raised); }

Pulse, not shimmer: a slow opacity change reads as "waiting" without a sweep that draws the eye.

Accessibility

Role and pattern

The skeleton shapes are aria-hidden. The region that is loading is aria-busy="true" and has a role="status" label ("Loading recent rides"); when data lands, aria-busy goes false and the content is read normally. No APG widget; see the aria-busy state.

Keyboard

KeyAction
TabSkips the skeleton; nothing inside is focusable until the content arrives.

Focus

Focus does not move into a loading region. If focus was on a control that is replaced, put it back on the same control once the content lands.

Labelling

One label for the whole region, not one per shape. Never read placeholder text.

Motion

Pulses over --duration-pulse (1.6 s). Under reduced motion the pulse duration is 0 and the shape holds still.

Touch

Not a target.

Content

  • No placeholder words ("Loading…", grey filler text). The shape is the message; the region label says what is loading.
  • Match line counts and widths to real copy (a class title is one line, about 70% of the card).
