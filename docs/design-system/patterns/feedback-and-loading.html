Pattern

Feedback and loading

Every press gets an answer, sized to what happened. A button that waits for the bike changes its own label; a search says what it is looking for; a dropped bike covers the part of the screen that stopped working. Telo Ride never shows a loading state for data that cannot be slow.

Overview

Telo Ride runs on the rider's own machine. Rides, levels, maps and classes are read from local data at once, so pages open whole. Waits only happen where the outside world is involved: a Bluetooth scan, pairing with the bike, the bike going quiet, a feedback note leaving the device, a YouTube player loading. Feedback design is about those moments.

The answers, from smallest to largest:

  1. In place: the control itself changes. Pair Echelon EX-5s → Pairing… → Paired; I'm ready → You're ready.
  2. Inline status: a sentence where the result will appear. “Looking for bikes nearby…”, “MarcoVelo left. Their seat is open again.”
  3. Banner: news about the whole page. “Neon Docklands is open.”, “Open Telo Ride in Chrome or Edge.”
  4. Overlay: the part of the screen that stopped working is covered, with one way to recover. “Lost the bike”, “Connect your bike”, “Turn on Bluetooth”.
  5. Dialog or panel: the rider has to decide, or the result replaces a form. “Leave this ride?”, “Feedback sent”.

Components used: Button, Spinner, Skeleton, Progress bar, Inline message, Alert and banner, Toast, Dialog and Device list.

Why the mocks have no loading states

Every screen's manifest entry marks loading as not applicable with the same reason: “every screen reads local, synchronous data (shared/game.ts, shared/videoWorkouts.ts), so there is nothing to wait for.” That is the rule, not a gap:

  • Never draw a loading state for data that cannot be slow. A page reading IndexedDB or a bundled catalogue renders complete on the first frame. A spinner there would only flash.
  • Draw one wherever the outside world answers: Bluetooth, the network, a video player, a GPU warming up a 3D world.
  • Match error states to the same rule. The manifest also says “nothing on it is fetched, so nothing can fail to load”. The errors Telo Ride draws are the outside world's: Bluetooth off, the wrong browser, plain http, the bike going quiet. See Empty and error states.

Optimistic updates

Anything that only changes local state takes effect on the press, with no wait drawn: I'm ready flips to You're ready, a preset chip loads its plan into the ladder, a resistance step moves the level. If a command to the bike then fails, the bike's reported level wins and the readout corrects itself; the Sent to bike log shows what was acknowledged. Don't use optimistic updates for anything that leaves the device (feedback) or ends something (End, Leave).

Loading states that are not drawn

Home, Map Select, Race Setup, the lobby, Results, Class Library, Class Start, Profile and Custom Setup have no loading or fetch-error state, by the rule above. If a screen ever reads from the network (a live peer list, a group session count), it gets a skeleton in the region that waits, never a page spinner, and the rest of the page renders.

Accessibility

Announcements

  • Waits and results the rider asked for are polite: role="status" on “Looking for bikes nearby…”, on the lobby notice, on the unlock banner and on the sent panel. Sending adds a visually hidden status, “Sending your feedback…”.
  • Things that stop the ride are assertive: role="alert" on Lost the bike and on the browser notice and panel.
  • The spinner icon is aria-hidden; the words beside it carry the meaning.
  • A region filling with a skeleton gets aria-busy="true" and a label; the skeleton blocks themselves are hidden.
  • Progress bars are role="progressbar" with aria-valuenow, min, max and a label (“Interval progress”).

Focus

Pressing a button must not lose focus. A disabled button drops focus to the page in most browsers, so the pressed button goes busy with aria-disabled="true" and ignores further presses, as the examples above do. When an overlay appears, focus moves to its one action (Reconnect); when it lifts, focus returns to where it was.

Motion

Spinners and skeletons read --duration-loop and --duration-pulse, which drop to 0 under prefers-reduced-motion: the spinner holds still as an icon and the skeleton as a flat block. The words still say what is happening, so nothing is lost.

Touch

Recovery actions in overlays are 44px tall (--target-comfortable), larger than page buttons, because they are pressed mid-ride.

Content

  • Say what is happening, with a verb in progress and one ellipsis character: “Looking for bikes nearby…”, “Pairing…”, “Sending…”. Never “Loading…” alone, never “Please wait”.
  • A waiting button says why it waits: Searching… rather than a greyed Pair.
  • Done is short and past tense: Paired, Feedback sent, You're ready.
  • Overlays name the problem, then the way out: “Lost the bike” / “Pedal to wake the bike and you’ll rejoin where everyone is.” / Reconnect.
  • Say what keeps going: “The class keeps going.”, “your ride is saved at 6:52”, “The ride is paused while you decide.”
