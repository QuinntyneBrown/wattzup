Pattern

Forms

Telo Ride has two forms and one confirmation. Custom Setup builds a ride from choices that are never wrong; the Feedback panel takes one note and sends it; Leave this ride asks before anything is lost. This page is the rule book for all three and for any form added later.

Overview

A form in Telo Ride is short, starts from a sensible value and says what pressing its button will do. There are two shapes:

  • Configuration form (Custom Setup, /profile/custom). Every control already holds a valid value: the page opens on the GCN 30-min HIIT ladder, never blank. Each change redraws the Your ride preview at once, so there is nothing to save and nothing to validate. The only action is Start ride.
  • Submission form (Send feedback, opened from the custom ride header). One choice of kind, one message, one optional checkbox, one button named for what happens: Report bug, Send idea or Send kudos. It then shows Sending… and Feedback sent.

The third piece is the destructive confirmation: Leave this ride? stands between the rider and a ride they would lose.

Components used: Form field, Text field, Textarea, Checkbox, Radio group, Switch, Slider, Number stepper, Chip, Button, Form layout, Popover and Inline message.

When to use

The rider needs to…UseIn the mocks

Confirm losing workA confirmation popover or dialog that names what is at stake and offers the safe way out first.Leave this ride?
Pick one of a few optionsA segmented control or radio cards, not a select. A select only past about seven options.Pack strength, Training mode, Type of feedback

Don't ask for what the app can read. The bike comes from Bluetooth, the ride snapshot is attached to feedback for the rider, and the YouTube link fills in from the plan. Every field you add is one more thing to get wrong mid-ride.

Layout rules

  • One column. A form never sets fields side by side unless they are one value split in two (Work and Recover in a ladder row). Width: --setup-form-max for page forms, 25rem for panels.
  • Label above the control, in .field__label (14px medium, muted). Hint text under the label or field in .field__hint. Error text directly under the field in .field__error.
  • Group related controls with role="group" (or radiogroup) and aria-labelledby pointing at their visible label: steppers, chip sets, the kind picker.
  • Space between groups is --space-8 to --space-10; inside a group, --space-2 to --space-4. Hairline rules (--color-line) split sections that change topic, like the video block.
  • The primary action comes last in reading order: the foot of the summary, the right of the panel footer. One primary per form.

Validation timing

The mocks draw no invalid state: Custom Setup cannot hold a wrong value, and the Feedback panel keeps Send disabled until there is a message. When a field can be wrong (a pasted link, a typed offset), validate like this:

  1. On blur, not on keystroke. Check a field when the rider leaves it, and only if they changed it. Never flag a field while it is being typed into, and never flag an empty field the rider has only tabbed through.
  2. Re-validate on input once it has failed. After an error shows, check on every keystroke so the error disappears the moment the value is fixed.
  3. Validate everything on submit. One error: move focus to that field. Two or more: show an error summary at the top of the form, focus it, and link each line to its field.
  4. Keep what was typed. A failed send never clears the message.
  5. Disable the button only for a single, visible requirement. Feedback's one required field sits right above Send, so a greyed Send explains itself. Any longer form keeps the button enabled and explains errors on submit instead.

2 things to fix before you start

  • YouTube link: paste the whole link, starting https://
  • Ride 0:00 starts at: use minutes and seconds, like 0:12.0
Error summary: a danger banner, focused on submit, one link per error. Title states the count and the goal.System addition (no mock draws it)

Destructive confirmation: Leave this ride?

Pressing Library mid-ride pauses the ride and opens a confirmation under the button. It states what is at stake in the rider's numbers, says the ride is paused, and offers three ways out, safest first. End, by contrast, saves and leaves without asking, because nothing is lost.

Accessibility

Labelling

  • Every control has a visible label tied to it: <label for> for inputs, aria-labelledby for groups. Placeholders are examples, never labels.
  • Icon buttons name their action and their target: “Less Warm-up”, “Longer effort 3”, “Remove round 8”, “Close feedback”.
  • A value shown twice is read once. The large “24 / 32” beside a slider is aria-hidden because the range input reports its own value.
  • A disabled action points at its reason: aria-describedby="start-blocked" → “Needs the HTTPS page to reach the bike.”

Errors and status

  • Invalid fields get aria-invalid="true" and aria-describedby pointing at the error text. Colour is never the only signal: the error has an icon and words.
  • The error summary is role="alert" with tabindex="-1" and takes focus on submit.
  • Sending is announced through a visually hidden role="status" (“Sending your feedback…”); the sent panel is itself a status region.

Keyboard

KeyAction
Tab / Shift+TabMove between groups and fields in reading order. A radio group is one stop.
← → ↑ ↓Move the choice inside a radio group (Training mode, Type of feedback); change a slider by one level.
SpaceToggle a preset chip, the switch or the Attach diagnostics checkbox.
EnterPress the focused button. In the message box it adds a line; it never submits.
EscClose Send feedback (the note is kept until the ride ends); in Leave this ride? it means Keep riding.

Focus

Opening Send feedback moves focus to the message box; opening Leave this ride? moves it to Save ride and open library (the mock's autofocus), never to Discard. Closing either returns focus to the button that opened it. The page behind is inert.

Motion

The sending state has no spinner, only a colour change, so it needs no reduced-motion variant. The context disclosure's chevron turns over --duration-base, which is 0 under reduced motion.

Touch

All form controls are at least 24px (2.5.8); text inputs are 40px tall and the YouTube link 44px. The kind picker's cells are about 60px tall.

Content

  • Labels are nouns, short and in sentence case: “Work resistance”, “Warm-up”, “YouTube link”, “Ride 0:00 starts at”.
  • The one open question follows the kind: “What went wrong?” (Bug), “What could be better?” (Improvement), “What’s working for you?” (Kudos).
  • Placeholders are examples and start with “e.g.”: “e.g. Resistance stayed at L8 when the video dropped to recovery.”
  • Buttons say what happens: Report bug, Send idea, Send kudos, Start ride, Save ride and open library. Never Submit, OK or Yes.
  • Progress ends in an ellipsis (one character, …): Sending…, Pairing…, Searching….
  • Success says what happens next: “Thanks — we’re on it. Bug reports go straight to the team. If we need more detail, we’ll email you.”
  • Errors name the field and the fix: “Paste the whole link, starting https://”. No blame, no codes.
  • Confirmations put the stakes in numbers: “You’re 6:52 in with 2.24 km ridden.”

The full microcopy library lives in Content; Content and tone shows it applied.
