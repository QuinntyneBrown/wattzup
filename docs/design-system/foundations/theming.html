Foundation

Theming

Telo Ride is drawn dark. Every product page ships data-theme="dark"; light is an addition that re-points the same semantic tokens at paper instead of ink.

Overview

The design draws Telo Ride dark only: ink canvas, charcoal panels, bone text, signal orange for “you”. The system keeps that as the product's theme and adds a light theme (paper canvas, paper panels, deeper accent text) so the same components also work on a bright screen and in documents. Both themes are the same semantic tokens pointed at different primitives; no component knows which theme it is in.

  • Dark first. Every product page ships <html lang="en" data-theme="dark">. The mocks and this site do the same.
  • Light is an addition. It exists for riders and tools that ask for it (data-theme="light"), and it passes the same contrast checks. The design never drew it; see open question 5 in the mocks README.
  • Themes override one tier. A theme block changes semantic tokens only. Primitives never change; component tokens follow automatically.

How a theme is chosen

SituationWhat appliesSelector in tokens.css
Product page (always)Dark[data-theme="dark"]
Page or wrapper asks for lightLight:root, [data-theme="light"]
No attribute, OS set to darkDark@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }
No attribute, OS set to light, or a tool that reads :rootLight:root

The dark block and its prefers-color-scheme twin are byte-identical; edit one, copy it into the other. The contrast checker reads both. Each theme sets color-scheme too, so scrollbars, form controls and the caret follow it.

A rider-facing theme switch, if the product adds one, writes the attribute on <html> and remembers it. This site's toggle (top of the navigation, or press t) does exactly that.

How tokens.css is layered

1 · Primitives--palette-ink

Raw values on :root: the design's palette, the paper palette for light, the jersey colours. Only semantic tokens read them.

2 · Theme blocks--color-panel

The design's own names (ink, panel, raised, line, fg, muted, faint, the -fg text variants, status tokens, shadows), declared on each theme selector.

3 · Role aliases--color-bg-surface

Role names that point at the design names, declared on :root, [data-theme] so every theme wrapper re-resolves them.

4 · Component tokens--btn-bg

Declared on each block in components.css; alias tier 2 or 3. Re-theme one component by overriding these.

/* 2. Primitives (never change with the theme) */
:root { --palette-ink: …; --palette-panel: …; --palette-paper: …; --palette-paper-panel: …; }

/* 3. Light: an addition */
:root, [data-theme="light"] { color-scheme: light; --color-ink: var(--palette-paper); --color-panel: var(--palette-paper-panel); … }

/* 4. Dark: the design (and its prefers-color-scheme twin, identical) */
[data-theme="dark"] { color-scheme: dark; --color-ink: var(--palette-ink); --color-panel: var(--palette-panel); … }

/* 5. Role aliases, resolved again on every theme wrapper */
:root, [data-theme] { --color-bg-canvas: var(--color-ink); --color-bg-surface: var(--color-panel); … }

Why the aliases sit on [data-theme]

A custom property that refers to another is resolved where it is declared. If --color-bg-surface: var(--color-panel) lived only on :root, a <div data-theme="light"> inside a dark page would inherit the already-resolved dark value. Declaring the aliases on every [data-theme] element makes each wrapper resolve them again against its own theme, which is how the side-by-side examples on every component page work.

Two names for one decision

The design's code says bg-ink, text-muted, text-volt. The canonical semantic tokens keep those names, so anyone reading the design or the mocks finds the same words here. Adding a theme

  1. Add primitives for any new raw colours to the primitives block (--palette-…). Never put a raw value in a theme block when a primitive can hold it.
  2. Copy the dark block (section 4 of tokens.css) to a new selector, [data-theme="<name>"], and re-point every token in it. Declare every token the dark block declares, so nothing leaks through from :root.
  3. Set color-scheme to light or dark to match the canvas.
  4. Leave the role aliases alone. They already sit on [data-theme] and re-resolve for the new block.
  5. Add the theme to the contrast check and run check_contrast.py until every pair in contrast-pairs.json passes.
  6. Regenerate tokens.json with tokens_to_json.py and screenshot the component pages in the new theme.
[data-theme="night"] {               /* example name */
  color-scheme: dark;
  --color-ink: var(--palette-night);        /* new primitives added in step 1 */
  --color-panel: var(--palette-night-panel);
  /* … every other token the dark block declares … */
}

Re-theming a single component is a smaller job: override its component tokens on a wrapper, never its properties.

.unlock-card .btn { --btn-bg: var(--color-gold); --btn-fg: var(--color-on-fill); }

Contrast and colour preferences

PreferenceWhat tokens.css does
prefers-contrast: moreHairlines become strong borders (--color-border-default → --color-line-strong) and tertiary text becomes secondary (--color-fg-subtle → --color-muted), in both themes.
forced-colors: activeThe focus ring becomes Highlight; default and strong borders become CanvasText. The browser replaces the rest; icons follow because they stroke with currentColor.
prefers-reduced-motion: reduceInterface durations drop to 0 ms; timers keep their pace. See Motion.
prefers-color-schemeOnly used when a page sets no data-theme. Product pages always set dark.

In forced-colours mode, components must not rely on a background colour alone to show a state: selected options keep aria-pressed or aria-current, and the board's “You” row keeps its bold name.

Consuming tokens.json

tokens/tokens.json is generated from tokens.css by tokens_to_json.py in the W3C Design Tokens (DTCG) format. Never edit it by hand; change tokens.css and regenerate.

  • Groups follow the CSS name: --color-ink is color.ink, --duration-fast is duration.fast.
  • Each token has $type and $value; aliases are written {palette.ink}.
  • $value is the light (:root) value. The dark value, the CSS name and resolved hex values sit under $extensions["com.agent-toolkit"].
"ink": {
  "$type": "color",
  "$value": "{palette.paper}",
  "$extensions": {
    "com.agent-toolkit": {
      "css": "--color-ink",
      "resolved": "#f6f4ef",
      "themes": { "dark": { "$value": "{palette.ink}", "resolved": "#0a0b0d" } }
    }
  }
}

To build platform constants (Swift, Kotlin, a TypeScript theme object), read the dark values first, since dark is the product, and fall back to $value for tokens that do not change with the theme:

import tokens from './tokens.json' assert { type: 'json' };
const ext = (t) => t.$extensions?.['com.agent-toolkit'] ?? {};
const dark = (t) => ext(t).themes?.dark?.resolved ?? ext(t).resolved ?? t.$value;
export const ink = dark(tokens.color.ink);          // "#0a0b0d"
export const durationFast = tokens.duration.fast.$value; // "150ms"

Do and don't

Tokens

Theming adds no tokens of its own: it re-points the colour and shadow tokens documented on Color and Elevation. The theme hooks are attributes and media features:

HookValuesEffect
data-themedark, lightSets the theme for the element and everything inside it.
color-schemeset by each themeNative controls, scrollbars and the caret follow the theme.
prefers-color-schemedarkDark when no data-theme is set.
prefers-contrastmoreStronger borders and tertiary text.
forced-colorsactiveSystem colours for focus ring and borders.
