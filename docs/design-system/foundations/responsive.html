Overview

Telo Ride runs on whatever screen sits in front of the bike: a laptop on the handlebars, a tablet on a stand, a phone, a TV-sized monitor. The system is mobile first: base styles fit a 360 px phone, and min-width queries add space, columns and status as the screen grows. Two breakpoints do almost all the work.

  • 640 px (sm): the header nav moves inline beside the logo and the XP bar appears; panels get roomier padding; dialogs stop being bottom sheets.
  • 1024 px (lg): pages split into two columns (content and an aside), the bike's connection status joins the header, and the race HUD shows its resistance panel.
  • 768 px (md) only reveals the race standings and a few secondary HUD details; 1280 px caps the container.

Columns, gutters, margins and the breakpoint tokens themselves are on Layout. This page covers what each component does at each width, control heights, touch targets and how to test.

Control heights

Four heights for anything you press or type into. The design's working size is 36 px (h-9) for header links, icon buttons and segmented options, and 40 px (h-10) for buttons and inputs.

The skill's default scale is 32 / 40 / 48; Telo Ride's small step is 36 because the design draws it.
TokenValueUsed by
--control-height-smHeader nav links, .icon-btn, .segmented__option, .btn--sm, browser-notice actions.
--control-height-md.btn, .input, ride header Pause and End on desktop.
--control-height-lg.btn--lg page actions (Race, Join group, Go to the start line), .icon-btn--lg.

Touch targets

People press Telo Ride with sweaty fingers, at 90 rpm, from arm's length. Three target tokens set the floor.

TokenValueRule
--target-minWCAG 2.5.8: every target at least 24 × 24, or 24 px clear of its neighbours. Range sliders are 24 px tall for this reason.
--target-comfortablePrimary actions on phones and in overlays: Reconnect, Ride Neon Docklands, the YouTube link field.
--target-rideAnything pressed while riding: resistance steppers in the race and the class, and on phones the ride header's Pause and End.

The system follows the mocks: those buttons are --control-height-sm/-md from 640 px and --target-ride below it on the custom ride. Until the question is settled, new mid-ride controls use --target-ride at every width.

Touch and pointer rules

  • No hover-only information. Every hover change is decoration on top of something already visible: a colour, a zoom on a class cover. Locked maps say why in text, not in a hover card.
  • Do not grow targets on (pointer: coarse). They are already big enough everywhere; a laptop with a touchscreen should not get a different layout.
  • Spacing between small targets. Adjacent 36 px controls (header nav, segmented options) keep at least 4 px between them; ride steppers sit a whole readout apart.
  • Full-height screens use 100dvh (.app) so the phone's browser bar never covers the ride controls.
  • Fixed bottom elements (toasts, bottom sheets) add env(safe-area-inset-bottom) on phones with a home indicator.
  • Nothing depends on orientation (1.3.4). The race scene reframes its panorama when the screen is taller than it is wide, and every page works in both.
  • Reflow (1.4.10): every page works at 320 px CSS width with no sideways scroll; only wide tables and the plan chart scroll inside their own wrapper.

Usage

/* Mobile first: the base is the phone, queries only add */
.results { display: grid; gap: var(--space-8); }
@media (min-width: 64rem) {
  .results { grid-template-columns: minmax(0, 1fr) var(--results-aside-width); gap: var(--space-14); }
}

/* Mid-ride controls: the ride target, at every width */
.class-resist__btn { width: var(--target-ride); height: var(--target-ride); }
