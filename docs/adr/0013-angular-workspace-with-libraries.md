# 0013. An Angular workspace with `components`, `api` and `wattzup` projects

- **Status:** Accepted, amended by [0016](0016-bike-only.md) (no treadmill, so `incline-control`, `machine-card` and the `Machine` type are gone); amended by [0017](0017-browser-edition.md) (a fourth project, `@wattzup/browser`, and a second composition root); amended by [0019](0019-no-backend.md) (one composition root binding every contract to `@wattzup/browser`; `@wattzup/api` holds contracts and hand-maintained types, with no HTTP implementation); amended by [0024](0024-telo-ride-workspace.md) (the Telo Ride workspace: `api`, `domain`, `components` and `ride`, and attribute components for router links)
- **Date:** 2026-11-17

## Context

`frontend/` was a single-project Angular workspace. The app `wattzup` sat at the workspace root,
about 50 component folders shared `src/app/dashboard/` whether they were small presentation parts
(`readout`, `num-stepper`, `toast`) or routed pages and orchestrating dialogs, and
`src/app/core/` mixed the code that talks to the backend with services and pure helpers. Nothing
kept a presentation component from injecting a store, nothing kept the API code from knowing a
route, and the components bore no consistent relation to the design system they render
(`docs/design-system/`).

L2-044 criterion 6 now asks for one workspace of three projects: a `components` library of
presentation components that match the design system, an `api` library for everything about
talking to the backend, and the `wattzup` application for everything else. What the rider sees,
the routes, the BEM classes, the bundle budget and the production output path do not change.

## Decision

**Three projects, generated by the Angular CLI, compiled from source by the application.**

- **Project locations.** All three are siblings under the workspace's `newProjectRoot`:
  `frontend/projects/components/`, `frontend/projects/api/` and `frontend/projects/wattzup/`. The
  app moves out of the workspace root so no project is special and each has its own `src/`,
  tsconfigs and `test` target, which is the layout `ng generate library` produces. Workspace-level
  tooling stays at the workspace root: `e2e/`, `scripts/`, `public/` (the fonts and machine photos,
  used by the app's `assets`), `proxy.conf.json` and the Playwright configs. The app's global
  styles (`tokens.css`, `styles.scss`) move with it to `projects/wattzup/src/`.
- **How the app consumes the libraries.** TypeScript path aliases in `frontend/tsconfig.json`,
  `@wattzup/components` and `@wattzup/api`, point at each library's `src/public-api.ts`. The app
  compiles library source directly, so `ng serve`, `ng test` and tree-shaking work with no separate
  library build. The libraries are not published, so they have no `ng-packagr` build target and
  the CLI's `ng-package.json`, `tsconfig.lib.prod.json` and per-project ESLint configs are
  removed; a library build that no script runs would only rot, and one root ESLint config covers
  every project. Each library keeps a minimal private `package.json` with `"sideEffects": false`,
  without which the bundler cannot drop unused exports of the barrel (the initial bundle grew by
  about 5 KB gzipped without it). This departs from the generated library layout in those
  respects; publishing would need a new ADR.
- **Dependency direction.** `wattzup` → `components`, `wattzup` → `api`, `components` → `api`
  for types only (a component may name a contract type such as `Machine` in an input), `api` →
  nothing in the workspace. No library imports the application. An ESLint
  `no-restricted-imports` rule in `frontend/eslint.config.js` enforces the direction; it is lint,
  not a test.
- **What counts as presentation.** A component that renders a design-system component from inputs
  and reports interactions through outputs. It injects only framework services (`ElementRef`,
  `Injector`, the CDK `DialogRef`), never an app service, an API token or the router, and uses no
  `routerLink`. Where a component injected an app service only to read a value
  (`phase-banner`, `ride-clock`, `status-line`) or called an app helper only to format its inputs
  (`command-log`, `metric-list`, `effort-row`, `plan-strip`, `set-list`, `quick-speeds`), the
  parent computes the value with the same helper and passes it in; the new app helpers
  (`commandLogView`, `metricItems`, `effortRowView`, `setListView`, `liveConnectionStatus`) have
  unit tests. A pure helper that only one library component uses moves with it (`level-picker-input`
  with `level-picker`). The type of an input belongs to
  the component and is exported from `@wattzup/components`; app helpers that build it import it
  from there. A component whose job is orchestration stays in the app even when the design
  system names it: `app-bar`, `connection-banner`, `interval` (it links to `/setup` and reads the
  countdown), `ride-overlay` (it links to `/setup`), `ride-trace` (the power trace's renderer host),
  `ride-video` and `video-link` (the YouTube player), `toast-region`, the pages and the dialogs.
- **Component names.** A component in `components` takes the name of the design-system component it
  renders, in its TypeScript class, file, folder and `wz-` selector: `num-stepper` →
  `number-stepper`, `cmd-log` → `command-log`, `mode-cards` → `radio-group`, `metrics-strip` →
  `metric-list`, `ride-preview` → `ride-profile`, `level-slider` → `slider`, `toggles` → `switch`,
  `dialog-shell` → `dialog`, `load-error` → `empty-state`. A component the design system documents
  as part of another keeps its own name and is filed as that component's part (for example
  `incline-control` in speed-control, `presets` in chip). The BEM classes stay exactly as the mocks
  have them, because the mocks and the e2e locators use them. Two components the design system
  lacked, `machine-card` (with `signal-bars`) and `effort-row`, get design-system pages first. The
  full mapping is in the host-and-structure design.
- **Shared SCSS partials.** The design-system partials (`_btn.scss`, `_badge.scss`, `_field.scss`
  and the rest) move to `projects/components/src/styles/design-system/`. The app's
  `stylePreprocessorOptions.includePaths` points at `projects/components/src/styles`, so every
  component keeps `@use 'design-system/btn'`.
- **Where `LiveStateService` lives.** In the app, because it owns live state and the reconnect
  policy (L2-044 criterion 2). The stream's connection type (`StreamConnection`) and the token call
  (`BikeApi.eventToken`) are in `api`.
- **The API-key interceptor's redirect.** `api` knows no route. The interceptor still adds
  `X-Api-Key` and clears the key on a 401, then calls the `UNAUTHORIZED_HANDLER` injection token
  that `api` declares. `app.config.ts` binds it to the app's redirect to `/unlock?returnUrl=…`
  (L2-055). `SafeStorage`, which `ApiKeyStore` needs, moves to `api` and is exported for the app's
  stores.
- **Unit tests.** Each project has its own `test` target (`@angular/build:unit-test`, Vitest, as
  before) and specs move with their code. The unit-test builder needs a build target for its
  options; with no library build, the libraries' targets name `wattzup:build:development`, which
  also gives them the SCSS include paths. `npm test` runs `ng test`, which runs every project's
  target. `npm run build` builds `wattzup`, still to `dist/wattzup/browser`.

## Consequences

- A presentation component can be read, reviewed and reused without the app: its inputs and
  outputs are its whole contract.
- Pages compute a little more: view values that components used to fetch now arrive as inputs.
  The helpers that compute them stay in the app with their unit tests.
- Every path under `frontend/src/app/` in the docs moved; designs and ADRs name the new paths.
- AGENTS.md's folder tree and Frontend rules describe the three projects. Its rule that pure helpers
  live under `src/app/core/` now reads per project: helpers stay with the project that owns them.
  This was a conflict between that rule and the library boundary, corrected in AGENTS.md here.
- `ng serve`, `ng build` and Playwright's web server name the `wattzup` project, since a
  workspace with several projects has no default one.
- Design-system components with no Angular counterpart today (button, chip, link, badge, tooltip,
  skeleton) stay SCSS partials; turning them into components is a later change.
